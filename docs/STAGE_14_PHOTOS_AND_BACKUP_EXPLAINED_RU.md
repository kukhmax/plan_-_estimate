# Stage 14 — как работают фото и бэкап: простым языком

> Это обзор для владельца и для тех, кто будет переносить или поддерживать проект. Он **не заменяет** технические
> документы (ссылки в конце) и **не содержит секретов**: ни ключей, ни паролей, ни токенов — они хранятся только в
> окружении сервера. Состояние описано на **2026-10-06**: код и инфраструктура готовы, бэкап проверен,
> **загрузка фото в production выключена** (`PHOTO_UPLOADS_ENABLED=false`) до отдельного решения владельца (Stage 14E).

---

## 1. Коротко

Фото — это «доказательства» на объекте: состояние стены до работ, дефект, скрытые работы. Приложение:

1. принимает фото с телефона (через Telegram Mini App);
2. проверяет его и делает из него три файла: **оригинал**, **средний** (для просмотра) и **маленький** (миниатюра);
3. кладёт файлы в **приватное облачное хранилище** (Cloudflare R2), а в базе данных (PostgreSQL) хранит только запись
   «какое фото, к какому объекту/помещению/поверхности/проёму относится»;
4. показывает фото владельцу по **временным ссылкам** (живут 5 минут);
5. отдельной командой делает **независимую резервную копию** базы и всех фото в **другом облаке** (Oracle Object
   Storage), заранее зашифровав базу.

```text
Телефон (Telegram Mini App)
   │  HTTPS
   ▼
Cloudflare (DNS/защита домена)  ──►  Caddy на сервере Oracle  ──►  Backend (FastAPI)
                                                                       │
                       ┌───────────────────────────────────────────────┼─────────────────────────┐
                       ▼                                               ▼                         ▼
              PostgreSQL (данные,                         Cloudflare R2 (файлы фото,     (по команде) бэкап:
              записи о фото)                              приватный bucket)              ─► Oracle Object Storage
```

Важно не путать два разных «Cloudflare»: **Cloudflare перед сайтом** (адрес `plan-estimate.pl`, защита, TLS) и
**Cloudflare R2** (хранилище файлов). Это разные сервисы одной компании.

## 2. Кто за что отвечает

| Компонент | Что делает | Где живёт |
|---|---|---|
| **Backend** (FastAPI) | принимает загрузку, проверяет, обрабатывает, пишет в хранилище и БД, выдаёт временные ссылки | сервер Oracle (Docker) |
| **PostgreSQL** | записи о фото (`photo_assets` — сам файл и его три объекта; `photo_attachments` — к чему фото привязано, подпись, категория, «включить в отчёт») | сервер Oracle (Docker) |
| **Cloudflare R2** | хранит сами файлы фото; bucket **приватный** — зная адрес файла, его открыть нельзя | облако Cloudflare, юрисдикция EU |
| **Caddy** | принимает HTTPS, ограничивает размер запроса загрузки (27 МБ) | сервер Oracle (Docker) |
| **Oracle Object Storage** | **независимая копия**: шифрованная база + копии фото; другой провайдер, чтобы одна авария не уничтожила всё | облако Oracle, Франкфурт |
| **Образ `backup`** | делает дамп базы и шифрует его (`age`) | сервер Oracle, по команде |
| **Образ загрузчика** (`backup-upload`) | копирует запуск в Oracle и проверяет его (`upload`, `verify`) | сервер Oracle, по команде |
| **Рабочая станция владельца** | единственное место с закрытым ключом шифрования; здесь проверяют и восстанавливают бэкап | ваш компьютер |

## 3. Что происходит при загрузке фото (когда она включена)

1. Приложение отправляет файл на `POST /api/projects/{проект}/photos` вместе с `upload_id` (случайный номер загрузки) и
   привязкой: проект, помещение, поверхность или проём.
2. Backend проверяет, что проект принадлежит этому пользователю; принимает файл **частями** во временную папку с
   ограничениями: до **25 МБ**, не более **60 мегапикселей**, нет данных дольше **60 секунд** — загрузка отклоняется.
3. Определяет формат **по содержимому**, а не по расширению. Разрешены **JPEG, PNG, WebP**. HEIC (формат iPhone по
   умолчанию) пока **не включён**; что именно отдаёт Telegram на iPhone и Android, проверяется на реальных телефонах в 14E.
4. Делает три объекта: **оригинал** (байты без изменений), **display** (JPEG, длинная сторона 2048 px, поворот по EXIF
   применён, **все метаданные удалены**), **thumbnail** (JPEG, 480 px). Считает контрольную сумму SHA-256.
5. В БД создаётся запись со статусом `PENDING` (она никому не видна), затем три объекта кладутся в R2 и запись получает
   статус `READY`. Если что-то сломалось — `FAILED`, и это видно администратору. **Незавершённые фото никогда не
   показываются.**
6. **Повтор безопасен:** если связь оборвалась, приложение повторяет загрузку с тем же `upload_id` — дубля не будет.
   Тот же номер с другими байтами — отказ (409).
7. Есть **квота**: предупреждение с 8 ГБ, мягкий предел 10 ГБ — после него новые загрузки аккуратно отклоняются, а
   просмотр продолжает работать. Сервер небольшой, поэтому нагрузка ограничена: одновременно принимается не больше **двух** загрузок, а тяжёлая
   обработка изображения идёт **по одной**; лишний запрос получает вежливый отказ «занято, повторите».

**Что хранится:** ключи объектов состоят только из UUID (никаких имён клиентов и файлов). Файлы **не перезаписываются и
не удаляются** — «убрать» фото можно только архивированием записи (оно скрывается, файл остаётся). **GPS из фото не
извлекается и не сохраняется.**

### Просмотр

Список фото отдаёт миниатюры по **временным подписанным ссылкам** (по умолчанию 300 секунд, настраивается). Каждая
ссылка открывает ровно один файл и только после проверки, что проект ваш. Оригиналы клиенту **не отдаются** вообще:
«скачать оригинал» в версии 1 нет (оригинал нужен будущему отчёту/PDF, он читается на стороне сервера).

## 4. Как работает резервная копия

**Зачем отдельная копия.** R2 надёжен, но «вторая копия у того же провайдера» не защищает от потери аккаунта, ошибочного
удаления или сбоя провайдера. Поэтому копия лежит **у другого провайдера** (Oracle), под другими ключами.

### Что делает один запуск (его выполняет владелец вручную)

1. **`db-dump`** — на сервере снимает «снимок» базы (один согласованный момент) и делает дамп. Дамп **сразу
   шифруется** публичными ключами `age` и сохраняется локально. Права доступа к базе у бэкапа — **только чтение**
   (отдельная роль `pe_backup`).
2. **`upload`** — копирует запуск в Oracle: зашифрованный дамп, **манифест** (список всех объектов с контрольными
   суммами) и в конце файл **`COMPLETE.json`** («печать»: запуск целый). Если в базе есть готовые фото, то все их три
   объекта копируются из R2 в Oracle с перепроверкой SHA-256. Запуск без `COMPLETE.json` считается **незавершённым** и
   для восстановления не годится.
3. **`verify`** — читает запуск из Oracle и перепроверяет печать, манифест и хеши. Его можно запускать и с сервера, и с
   рабочей станции — это два независимых читателя.

### Кто что может (минимальные права)

| Участник | Что может | Чего не может |
|---|---|---|
| Роль БД `pe_backup` | читать базу | писать, менять схему |
| Загрузчик на сервере (по идентичности сервера Oracle) | **создавать** новые файлы в бакете бэкапа, читать их | перезаписывать, удалять |
| Токен R2 для бэкапа | **читать** бакет с фото | писать, удалять |
| Restore-пользователь (на время проверки) | читать бакет бэкапа по временному API-ключу | что-либо менять; ключ **удаляется** после проверки |
| Сервер | ничего не знает о закрытом ключе шифрования | расшифровать бэкап |

Удалить что-то из бэкапа может только администратор в консоли Oracle. Это сделано специально: ошибка или взлом
сервера не смогут уничтожить копию.

### Шифрование и ключи

Дамп шифруется утилитой `age` для **двух публичных ключей**: **A** (рабочий: файл на вашем компьютере + копия под
парольной фразой на флешке) и **B** (аварийный: только на бумаге). Закрытые ключи **никогда не лежат на сервере**. Без
закрытого ключа бэкап базы не прочитать — поэтому проверка, что ключ A реально расшифровывает, обязательна (она
сделана 2026-10-05).

### Восстановление (проверено)

1. На рабочей станции поднимается чистая временная PostgreSQL.
2. `restore` скачивает запуск из Oracle (по API-ключу restore-пользователя), проверяет хеши, расшифровывает ключом A и
   загружает в временную базу; затем (если есть фото) восстанавливает файлы.
3. Сверка: число строк во всех таблицах равно боевой базе, версия миграций — как в коде.

Так 2026-10-06 был восстановлен первый боевой бэкап, и данные совпали.

## 6. Можно ли запускать на других серверах?

**Да, но разные части переносятся по-разному.**

| Часть | Переносимость | Что нужно |
|---|---|---|
| Приложение (backend, фронтенд, PostgreSQL) | **любой Linux с Docker Compose** (проверено на Oracle ARM64; код проверялся и на amd64) | Docker + Compose, домен и HTTPS (у вас Caddy + Cloudflare) |
| Хранение фото | **любое S3-совместимое хранилище** с HTTPS (Cloudflare R2 — текущее; подойдут AWS S3, Backblaze B2, MinIO и т. п.) | `MEDIA_S3_*` в окружении; приватный bucket; поддержка подписанных ссылок (presigned GET). Для R2 регион `auto` |
| Резервная копия: образы `backup` и `restore`, шифрование, манифест | **переносимо** (это обычные Docker-образы; amd64 и ARM64) | PostgreSQL 16, `age`, свой набор ключей |
| Резервная копия: **цель** (Oracle) | **привязана к Oracle**: код использует Oracle SDK и два способа входа — идентичность сервера (`instance principal`, работает **только** на сервере Oracle с настроенной политикой) и API-ключ | Чтобы перенести бэкап на другой облачный сервер, нужно либо оставить Oracle как цель (с API-ключом вместо идентичности сервера), либо **написать адаптер** для другого хранилища (в коде цель выделена как отдельный интерфейс, но другой реализации сейчас **нет**) |
| Защита от кражи прав сервера (IMDS-guard, сеть `pe-upload`) | специфична для Oracle | На другом провайдере нужны свои аналоги |

**Если сервер потерян целиком:** поднимается новый сервер по `PRODUCTION_DEPLOYMENT_RUNBOOK_RU.md`, база
восстанавливается из бэкапа в Oracle ключом A, а фото остаются в R2 (если R2 цел) или копируются из Oracle. Это
пошаговая процедура (раздел 72 руководства), уже отработанная на рабочей станции.

## 7. Какие настройки нужны

Все значения задаются **только в окружении сервера** (`.env.production`), в Git их нет. Шаблон —
`.env.production.example`.

### Хранение и загрузка фото (backend)

| Переменная | Значение по умолчанию | Смысл |
|---|---|---|
| `MEDIA_STORAGE_BACKEND` | `disabled` | `s3` — хранилище подключено; `disabled` — фото недоступны |
| `MEDIA_STORAGE_NAME` | `r2-primary` | логическое имя хранилища (записывается в БД, нужно при будущем переезде) |
| `MEDIA_S3_ENDPOINT_URL` | пусто | адрес API хранилища, обязательно `https://…` |
| `MEDIA_S3_BUCKET` | пусто | имя приватного bucket |
| `MEDIA_S3_REGION` | `auto` | регион (для R2 — `auto`) |
| `MEDIA_S3_ACCESS_KEY_ID`, `MEDIA_S3_SECRET_ACCESS_KEY` | пусто | ключи доступа **с правом записи** только для backend (секрет) |
| `PHOTO_UPLOADS_ENABLED` | `false` | **главный выключатель загрузки**; `true` допустим только вместе с `MEDIA_STORAGE_BACKEND=s3` |
| `PHOTO_SIGNED_URL_TTL_SECONDS` | `300` | сколько живёт ссылка на просмотр (60–3600) |
| `PHOTO_MAX_UPLOAD_BYTES` / `PHOTO_MAX_REQUEST_BYTES` | 25 000 000 / 27 000 000 | предел файла и всего запроса (Caddy тоже режет на 27 МБ) |
| `PHOTO_MAX_DECODED_PIXELS` | 60 000 000 | защита от «бомб» из пикселей |
| `PHOTO_STORAGE_WARNING_BYTES` / `PHOTO_STORAGE_SOFT_CAP_BYTES` | 8 ГБ / 10 ГБ | предупреждение и мягкий предел квоты |
| `PHOTO_TEMP_DIR`, `PHOTO_TEMP_STALE_AFTER_SECONDS`, `PHOTO_PROCESSING_WAIT_SECONDS` | `/tmp/plan-estimate-photos`, 86400, 30 | временные файлы и ожидание обработки |

### Резервная копия (на сервере, отдельные файлы вне Git)

| Файл / переменная | Смысл |
|---|---|
| `…/db-backup/secrets/pgpass` (0600) | пароль роли `pe_backup`; только в этом файле, не в переменных |
| `secrets/backup.env`: `BACKUP_UID`, `BACKUP_GID`, `BACKUP_HOST_ROOT`, `BACKUP_PGHOST`, `BACKUP_PGPORT`, `BACKUP_PGDATABASE`, `BACKUP_PGUSER`, `BACKUP_PGSSLMODE`, `BACKUP_AGE_RECIPIENTS` | подключение к базе и **публичные** ключи `age` |
| `secrets/upload.env`: `BACKUP_UPLOAD_S3_*` (токен R2 **только чтение**), `BACKUP_UPLOAD_SOURCE_NAME`, `BACKUP_OCI_NAMESPACE`, `BACKUP_OCI_BUCKET`, `BACKUP_OCI_REGION`, `BACKUP_TOOL_COMMIT` | откуда копировать и куда |

В Oracle заранее настраиваются: bucket бэкапа (с версионированием), политика «только создание объектов» для сервера,
группа «только чтение» для восстановления. Подробный порядок — `docs/STAGE_14D3_ORACLE_BACKUP_PROVISIONING.md`.

## 8. Что **не** делает версия 1

- нет удаления файлов и «скачать оригинал» (архивирование прячет запись, файл остаётся);
- HEIC не принимается (решение — после проверки на реальных телефонах);
- нет фото осмотров/замечаний, меток на фото, фото выполнения работ (14F–14H) и отчёта с фото (14I);
- нет расписания бэкапов и автоматической очистки бакетов;
- интерфейса для загрузки фото в приложении ещё нет (это 14E) — backend готов, но без включения флага и без экранов
  загрузить фото нельзя.
