# Шифрование данных клиентов, шаг EN-2b-3 — расчёты («Faktury i zaliczki»)

Статус: **EN-2b-3 готов локально (2026-10-18), не выложен.** Бэклог-пункт, **не этап дорожной карты**. Начат по вашему «да» после приёмки AC-6. Предыдущие шаги: EN-2a, EN-2b-1, EN-2b-2 (приняты / выложены).

## 1. Что шифруется

Четыре колонки таблицы `project_payments` (счета, авансы, платежи, расходы объекта):

| Колонка | Что в ней |
|---|---|
| `title` | за что запись («Faktura za etap 1», «Farba dla Kowalskich») |
| `number` | номер счёта / документа |
| `counterparty` | магазин / поставщик расхода |
| `note` | заметка |

* **Остаётся открытым:** суммы (брутто, нетто, ставка VAT), даты (операции, срок), вид записи, категория расхода, связь платёж → счёт, флаг архива. Итоги, остатки и сроки счетов считаются по ним на сервере (поэтому их шифровать нельзя без потери расчётов). Это деньги и даты без имён и описаний.
* Фото чеков, названия объектов (уже зашифрованы в EN-2a), PDF «Rozliczenie» (строится из расшифрованных записей при выдаче и живёт в чате).
* **Не входят** в этот шаг (решение — по вашему слову): свободные заметки помещений и осмотров, тексты своих напоминаний в календаре, подписи к фото. Напоминания о сроках счетов хранят только ключ текста, а название счёта подставляется при отправке.

## 2. Миграция 0064 (без потери данных)

* `title` (VARCHAR 500), `number` (64), `counterparty` (255) → **TEXT**; `note` уже TEXT. Значения не меняются, старые читаются как раньше; шифртекст длиннее прежних пределов.
* Проверка «название не пустое» в базе остаётся (пустое название отклоняет сервис до шифрования).
* Откат миграции **откажет**, пока в этих колонках есть шифртекст.

## 3. Порядок выкладки (скрипт сам делает всё по порядку)

Строгое чтение на время миграции и перекодировки **временно выключается** и включается обратно на воротах S (как в EN-2b-2).

1. **Бэкап A9 под голову 0063 не старше суток** — он нужен до миграции. Образы бэкапа собираются из ветки, чья последняя миграция совпадает с базой; после EN-2b-3 ветка заканчивается миграцией 0064, поэтому новый бэкап под 0063 из неё сделать нельзя. Подходит бэкап после выкладки AC-6: `20261018T184145Z-5350c7a6`; скрипт сам проверяет возраст (≤ 24 ч) и показывает номер.
2. Скрипт (в **новой** сессии):
   `cd ~/apps/plan_-_estimate && git fetch -q origin backlog-client-encryption && git show origin/backlog-client-encryption:docs/CLIENT_ENCRYPTION_EN2B3_DEPLOY_RU.sh > ~/deploy_en2b3.sh && bash ~/deploy_en2b3.sh`
3. Ворота **M**: `МИГРАЦИЯ 0064 ДА` — миграция + пересоздание backend (30–60 секунд); скрипт проверяет: 4 колонки TEXT, число строк то же.
4. Ворота **R**: `ПЕРЕКОДИРОВКА ДА` — старые значения → шифртекст, затем `verify`: открытых 0, нерасшифровываемых 0.
5. Ворота **S**: `СТРОГОЕ ЧТЕНИЕ ДА` — строгое чтение включается; скрипт читает **все строки 12 зашифрованных таблиц** в строгом режиме и сверяет число строк с базой.
6. После `ВСЁ PASS`: чек-лист (раздел 4), затем бэкап под новую голову: `BACKUP_BRANCH=backlog-client-encryption BACKUP_HEAD=0064_encrypted_payments bash ~/backup_a9.sh`.

Скрипт можно запускать повторно: он узнаёт, что миграция уже применена, не двигает тег `pre-en2b3` и не требует лишних ворот. Frontend не меняется.

## 4. Чек-лист после выкладки (на телефоне, PL и RU)

* Объект → «Faktury i zaliczki»: старые записи (счета, авансы, платежи, расходы) на месте — название, номер, магазин, заметка.
* Добавьте новый расход и новый счёт, измените существующую запись, сохраните, откройте снова.
* Проведите платёж по счёту: остаток и итоги верны.
* «Rozliczenie» (отправить / черновик): PDF приходит в чат, названия записей на месте.
* Архив → «Faktury i zaliczki»: записи читаются (удаление — только открыть окно и «Anuluj»).
* Календарь: срок неоплаченного счёта по-прежнему даёт напоминание; клиенты, объекты, документы — как раньше.

## 5. Откат — порядок и предел

* **До ворот R:** миграция вниз командой из сообщения скрипта (`alembic downgrade 0063_encrypted_documents`), затем образ `pre-en2b3`; верните `DATA_STRICT_READ=true`, если он был.
* **После перекодировки** образ до EN-2b-3 записи расчётов не прочитает, откат миграции откажет: только **вперёд** новым выпуском или из бэкапа A9.
* Строгое чтение выключается без потерь (`DATA_STRICT_READ=false`, пересоздать backend). `DATA_KEK` по-прежнему нельзя терять и менять.

## 6. Что проверено

* `backend/tests/test_en2b3_payments.py` (12): список колонок совпадает с миграцией, запись шифртекстом и чтение как написано, пустые остаются `NULL`, команда перекодировки превращает настоящие старые записи (читаются прежними значениями), строгое чтение отклоняет открытое название, миграция вверх / вниз и отказ отката.
* Весь backend-набор в обычном режиме и **с включённым шифрованием в каждом тесте** (`EN_TEST_ENCRYPTION=1`); PostgreSQL 16, скрипт на заглушках, мутации — результаты в `docs/development-progress.md`.
