# Stage 16 — Договоры и защитные протоколы: аудит и план

Статус: **план 2026-10-09 (16A), старт одобрен владельцем («начинаем новый этап на новой ветке»), решения владельца Q1–Q8 ещё не приняты**; реализация идёт подэтапами 16B–16H, каждый — одним логическим коммитом, выкладка только по явному «да» владельца. Ветка `stage-16` (от `main` = `848d360`, Stage 15 закрыт). Дорожная карта: `docs/development-progress.md` (строка Stage 16: «Contracts and protective protocols»; в плане развития: «Binding contract generator, site handover protocol, concealed works, final acceptance»). Предыдущий этап дал для этого **движок PDF, журнал выданных документов, профиль исполнителя, каркас четырёх видов документов (без слов)** — `docs/STAGE_15_DOCUMENTS_PDF_PLAN_RU.md`. Юридическая база знаний и поиск по ситуациям — **Stage 17**.

## 1. Что такое Stage 16 и чем он не является

**Входит:** договор (Umowa), три протокола (передачи объекта, скрытых работ, итогового приёмки) и «защитные» документы — те, что фиксируют информирование клиента о риске и его решение (например, отказ от рекомендованной грунтовки или армирования → оговорка об исключении ответственности исполнителя за трещины). Для каждого документа: данные (что и откуда берётся), **текст из серверного каталога положений** (никогда не из интерфейса), состояния и журнал, выпуск в PDF и отправка в чат владельца (как в 15F).

**Не входит:** электронная подпись (документ печатают и подписывают на бумаге); прямая отправка клиенту (владелец пересылает файл сам); база знаний Stage 17 (поиск норм, ссылки на PN-EN / ITB — появятся там и подключатся к положениям позже); календарь и напоминания (Stage 18); ИИ (в MVP запрещён: текст собирается детерминированно из каталога и данных).

## 2. Что уже есть и чего нет

| Тема | Состояние |

| Движок PDF, шаблоны, журнал, нумерация, отправка | **Есть (Stage 15):** `documents/` (Jinja2 + WeasyPrint в отдельном ограниченном процессе), `issued_documents` (номер `KOSZ/2026/10/08/1953`, порядковый номер по объекту, статусы, без файла), отправка ботом в чат владельца, экраны. Журнал принимает виды `ESTIMATE` и `PHOTO_REPORT` (CHECK в миграции `0038`) — для договоров и протоколов нужна своя миграция. |
| Каркас четырёх видов | **Есть (15G):** `CONTRACT`, `HANDOVER_PROTOCOL`, `CONCEALED_WORKS_PROTOCOL`, `FINAL_PROTOCOL` в реестре, один шаблон `skeleton.html.j2` (шапка, стороны, объект, пронумерованные секции, приложения, подписи), префиксы номеров `UMOWA`, `PRZEK`, `ZANIK`, `ODBIOR`, ключи секций без слов. Секция без текста печатает «— do uzupełnienia —». Тест запрещает слова-признаки положений в самом каркасе — текст приходит данными. |

Объект: адрес, город, индекс — есть. |
| Объём и цена | Смета: версии `DRAFT` / `FINAL` / `ACCEPTED`, строки-снимки, итог **без НДС** (решение Stage 15). | Сроки и технологические перерывы | Stage 13: планы работ, исполнение по поверхностям, технологические перерывы (сушка) — **данные есть**, дат начала / окончания договора **нет**. |

| Положения (клаузулы) | **Нет нигде.** Юридический текст сознательно не писался. Правила проекта: ни одного положения в React; юридические фрагменты — из серверного каталога. |
| Состояния документов | Журнал знает только «отправлено / не отправлено». Для договора и протоколов нужны **сохраняемые записи** (снимок условий), иначе нельзя повторить тот же документ при споре. |

## 3. Решения владельца (нужны до реализации)

Мои рекомендации — первыми; любой пункт можно изменить.

| № | Вопрос | Рекомендация |
|---|---|---|
| Q1 | **Кто пишет юридический текст положений.** Приложение не заменяет юриста: текст договора и оговорок должен быть вашим / одобренным юристом. | В Stage 16 я готовлю **каталог положений** (серверный JSON на польском, версионируемый, ключи секций из 15G) с **нейтральной стартовой редакцией** по общей структуре договора подряда и протоколов — как **черновик «wymaga weryfikacji prawnika»**; печатается документ только из утверждённой вами версии каталога (флаг `approved`), до утверждения — водяной знак «WERSJA ROBOCZA», как у черновика сметы. Утверждение — ваше решение, после просмотра юристом. |
| Q2 | **Что вводится при составлении договора** (переменные условия). | Из данных: стороны, объект, объём и цена (из версии сметы, без НДС). Вводится владельцем один раз на договор: дата заключения и место, сроки (начало / окончание работ, **с учётом технологических перерывов** из Stage 13), аванс (% и срок), порядок платежей (этапами или по приёмке), срок гарантии (мес.), неустойка (ставка или «нет»). Всё остальное — текст каталога. |
| Q3 | **НДС в договоре.** В Stage 15 решено «цена без НДС, НДС потом отдельно». | Договор печатает **ту же цену без НДС** с пометкой из каталога («netto») и без расчёта НДС; НДС — отдельным будущим решением. |
| Q4 | **Состояния договора.** | `DRAFT` (правка) → `ISSUED` (выдан PDF, условия **заморожены** как снимок) → `SIGNED` (владелец отмечает «подписан» с датой; смета при этом получает `ACCEPTED`) → `ARCHIVED`. Изменение выданного договора = **новая версия** (аннекс не в этом этапе). Подпись на бумаге вне приложения. |
| Q5 | **Какие протоколы и что в них из данных.** | **Передачи объекта**: адрес, состояние при передаче (отметки владельца + фото из Stage 14), доступ и коммуникации. **Скрытых работ**: список закрываемых работ (из Stage 13: выполненные, ещё не закрытые) + фото-доказательства (из Stage 14) + результат осмотра владельца. **Итоговый приёмки**: выполненный объём (по смете и исполнению), замечания (из Stage 6 / 14: находки и метки) и сроки их устранения. Подписи сторон на бумаге. |
| Q6 | **Защитные документы — какие сценарии.** | Первые два: (а) **«Информирование и отказ клиента»**: риск (из Stage 7) + рекомендованная работа / мера (из Stage 11) + решение клиента (принял / отказался) + оговорка об исключении ответственности исполнителя при отказе (текст из каталога) — **только для рисков с `warranty_exclusion_candidate`**; (б) **«Работы по просьбе клиента вопреки рекомендации»**. Дополнительные работы (аннекс к договору) — вне этого этапа. |
| Q7 | **Выпуск и доставка.** | Как в Stage 15: PDF в **ваш чат с ботом**, запись в журнале (`UMOWA/…`, `PRZEK/…`, `ZANIK/…`, `ODBIOR/…`, и порядковый номер документа по объекту). Отправка клиенту — вы пересылаете файл сами. |
| Q8 | **Порядок реализации.** | 16B данные и каталог положений → 16C договор → 16D протокол передачи → 16E протокол скрытых работ → 16F итоговый протокол → 16G защитные документы → 16H проверка и выкладка. Если для вас важнее другое (например, **протокол скрытых работ раньше договора**, потому что он нужен на объектах уже сейчас), порядок можно поменять. |

## 4. Предлагаемые подэтапы

| Подэтап | Содержание | Миграция |
|---|---|---|
| **16B** | Каталог положений: структура файла, версии, флаг утверждения, проверка полноты (каждая секция каркаса 15G имеет текст), загрузка, тесты «текст только из каталога»; адрес клиента (поля и экран) — по Q2 | `clients` (адрес), возможно `contract_*` |
| **16C** | Договор: таблица `contracts` (снимок условий, ссылка на версию сметы, состояния), сервис сборки секций из каталога и данных, PDF, журнал, экран «Договор» на объекте | `contracts`, расширение CHECK журнала |
| **16D** | Протокол передачи объекта | `protocols` (общая таблица видов) или своя |
| **16E** | Протокол скрытых работ (+ выбор выполненных работ и фото Stage 14) | — |
| **16F** | Итоговый протокол приёмки (объём, замечания, сроки устранения) | — |
| **16G** | Защитные документы (информирование и отказ клиента, работа вопреки рекомендации) | `client_decisions` |
| **16H** | Состязательная проверка (владельцы, архив, повторный выпуск, мобильный вид 320–412 px PL / RU, большие документы), миграции, пересборка образов бэкапа, runbook, выкладка по «да», проверка владельцем на телефоне | — |

Правила, которые действуют в каждом подэтапе: слова документов — только в каталоге на сервере; интерфейс (PL / RU) не содержит ни одного положения; детерминированно, без ИИ; все новые таблицы с `owner_id`, UUID, UTC, обратимая миграция Alembic; журнал не хранит файлы (документ воспроизводится из снимка); документ клиента — всегда польский; мобильный интерфейс первичен (экраны документов — как карточка «Dokumenty PDF» Stage 15).

## 5. Риски

| Риск | Что делаем |
|---|---|
| Юридически неверный или неполный текст положений | Каталог — черновик до вашего утверждения и просмотра юристом (Q1); водяной знак до утверждения; версия каталога пишется в каждый выданный документ; тесты проверяют полноту секций и запрет текста вне каталога |
| Спор о том, «что было в договоре» | Выданный договор — неизменяемый снимок условий и версии каталога; повторный выпуск воспроизводит тот же текст |
| Персональные данные клиента (адрес; PESEL — **не** храним) | Минимум полей; доступ только владельцу (`owner_id`); журнал без файлов; в логах — без значений |
| Нагрузка рендера | Тот же ограниченный процесс; замеры Stage 15: 60 фото ≈ 2 с, пик ≈ 72 МБ — запас большой |
| Объём этапа | Один документ за подэтап, каждый независимо тестируется и выкладывается только по вашему «да» |

## 6. Критерий готовности

Все подэтапы закоммичены, бэкенд- и фронтенд-тесты, `tsc`, `vite build`, PostgreSQL-проверка миграций, состязательная проверка; на телефоне владелец получает в чате бота PDF договора и протоколов, суммы / объём / фото совпадают с приложением, польский текст берётся из утверждённого каталога; результат записан в `docs/development-progress.md`; приёмка владельцем.
