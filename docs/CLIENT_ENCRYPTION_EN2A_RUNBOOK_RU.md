# Шифрование данных клиентов, шаг EN-2a (V1: ключ сервера) — порядок выкладки и работа с ключом

Статус: **EN-2a готов локально (2026-10-18), не выложен.** Бэклог-пункт, **не этап дорожной карты**. План: `docs/CLIENT_DATA_ENCRYPTION_PLAN_RU.md`.

## 1. Что меняется и что нет

* **Для вас в приложении — ничего видимого:** клиенты, объекты, представители, заметки выглядят и ищутся как раньше.
* **В базе:** поля клиента (имя, фамилия, фирма, телефон, e-mail, NIP, улица, индекс, город, Telegram, заметки), объекта (название, адрес, город, индекс, описание), представителя (имя, телефон, e-mail) и заметок объекта **записываются шифртекстом** `enc1:…` (AES-256-GCM). Должность представителя не шифруется (она никого не идентифицирует).
* **Ключи:** у каждого владельца свой ключ данных (таблица `data_keys`), он хранится **только завёрнутым** ключом сервера `DATA_KEK` (переменная окружения на VM). Ключ данных создаётся при первом входе владельца в приложение.
* **Старые значения остаются открытыми**, пока их не перекодирует команда шага **EN-2b** (по вашему отдельному «да»). До этого шифрование защищает только новые и изменённые значения; читается и то, и другое. **Защита от утечки дампа / бэкапа начинается полностью только после EN-2b.**
* **Документы** (PDF, снимки в журнале отправленных) в этом шаге **не шифруются** (EN-2b): в них полные данные клиента уже на момент выпуска.
* Поиск клиентов теперь выполняется в приложении после расшифровки (четыре индекса клиентов сняты). Для десятков и сотен клиентов это мгновенно.

## 2. Ключ `DATA_KEK` — главное

* Это 32 случайных байта в base64. **Потеря ключа = потеря данных, записанных шифртекстом:** из базы и из бэкапов его не восстановить (бэкап хранит тот же шифртекст, поверх — age).
* **Создаётся один раз, на VM:** `echo "DATA_KEK=$(openssl rand -base64 32)" >> ~/apps/plan_-_estimate/.env.production`.
* **Две копии вне сервера, до выкладки:** в менеджере паролей (запись «Plan & Estimate — DATA_KEK») и на бумаге в другом месте. Не в репозитории, не в чате, не в письме.
* **Отпечаток** — первые 8 знаков SHA-256 ключа: скрипт печатает его на воротах K, вы сверяете со своей копией (`printf '%s' "<копия>" | sha256sum | cut -c1-8`). Совпадает — копия верна.
* **Не менять ключ после первой выкладки** (ротация — отдельный шаг EN-3: перезавёртывание ключей данных без перешифровки).
* Ключ видят только процесс backend и тот, кто имеет доступ к `.env.production` на VM. Он **не** попадает в образ, репозиторий, логи, бэкапы. В Docker Compose он передаётся переменной окружения контейнера.
* Без ключа backend **не запускается** (так задумано: чтобы не записать данные открытым текстом по забывчивости).

## 3. Порядок

1. Свежий бэкап A9 под текущую голову (не старше суток): `BACKUP_BRANCH=main BACKUP_HEAD=0061_expense_category bash ~/backup_a9.sh` (в **новой** SSH-сессии, потом закрыть её).
2. Создать ключ (раздел 2), сохранить обе копии.
3. Запуск (в **новой** SSH-сессии): 
   `cd ~/apps/plan_-_estimate && git fetch -q origin backlog-client-encryption && git show origin/backlog-client-encryption:docs/CLIENT_ENCRYPTION_EN2A_DEPLOY_RU.sh > ~/deploy_en2a.sh && bash ~/deploy_en2a.sh`
4. Ворота **K**: сверить отпечаток, ввести `КЛЮЧ СОХРАНЁН <отпечаток>`. Ворота **M**: ввести `МИГРАЦИЯ 0062 ДА`.
5. После `ВСЁ PASS`: полностью закрыть и открыть Telegram → Mini App; пройти чек-лист (раздел 4).
6. Бэкап под новую голову: `BACKUP_BRANCH=backlog-client-encryption BACKUP_HEAD=0062_data_keys bash ~/backup_a9.sh`.

## 4. Чек-лист после выкладки

* Список клиентов, карточка клиента, поиск по фамилии / телефону / названию фирмы (в том числе с польскими и русскими буквами) — как раньше.
* Список объектов, создание объекта, заметка объекта, представитель объекта — сохраняются и читаются.
* Календарь: напоминания с названием объекта приходят как раньше (цикл сообщений читает названия после расшифровки).
* Архив: список архивных помещений / поверхностей упорядочен по названию объекта.
* Проверка шифртекста (печатает только числа и префиксы, не данные): после первого входа ключей данных = 1; после первого сохранения клиента запись с `enc1:` появляется:
  `docker exec plan_estimate_postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atc "select (select count(*) from data_keys), (select count(*) from clients where last_name like '\''enc1:%'\'')"'`

## 5. Откат — порядок и предел

* **Пока ничего не сохранено шифртекстом** (после выкладки и до первого сохранения клиента / объекта / заметки / представителя): откат безопасен — команда из сообщения скрипта (миграция вниз → прежний образ).
* **После первого сохранения шифртекстом** прежний образ данные не прочитает (увидит `enc1:…`), а откат миграции **откажется** (он не превращает шифртекст в нечитаемый текст). Назад пути нет — только **вперёд новым выпуском** или восстановление из бэкапа A9 (с потерей записей после бэкапа).
* Поэтому после выкладки проверяйте сразу, до первых рабочих записей.

## 6. Что проверено

* Модульные и интеграционные тесты (`backend/tests/test_en2a_*.py`): формат значения, подмена шифртекста в другую колонку / повреждение / неверный ключ — отказ; все поля клиентов, объектов, представителей, заметок хранятся шифртекстом и отдаются как были; поиск и сортировка после расшифровки; мягкое чтение старых значений; ключ на каждого владельца; перезапуск процесса (ключи из базы); неверный `DATA_KEK` — типизированная ошибка без данных; запись без ключа владельца отказывает (никогда не открытым текстом); календарный цикл читает названия в «свежем» процессе; production не стартует без ключа; миграция вверх / вниз, отказ отката при шифртексте.
* PostgreSQL 16: миграция 0061 → 0062 → откат → 0062; 12 одновременных первых запросов нового владельца создают ровно один ключ; старые открытые строки читаются; новые значения — шифртекст в базе; поиск; неверный ключ.
* Мутационная проверка: 32 из 33 искусственных поломок кода ловятся тестами (одна — избыточная защита, на поведение не влияет).
* Скрипт выкладки: полный проход и 16 отказов на заглушках `docker` / `curl` поверх настоящего git.
