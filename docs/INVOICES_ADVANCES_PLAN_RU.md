## 2. Что такое «договорная сумма» (вы спрашивали)

**Договорная сумма** — это **общая цена, о которой вы договорились с клиентом за всю работу на этом объекте** (например, «40 000 zł за ремонт квартиры»). Она нужна только для одного: показать **«сколько ещё осталось получить»** = договорная сумма − уже полученные деньги. Это не сумма фактуры и не сумма аванса; она одна на объект.

Откуда её брать: в приложении уже есть **смета** (Kosztorys) с итогом. Поэтому: **подсказываем сумму из принятой / итоговой сметы** («Kosztorys: 38 420 zł») и даём вам **поправить вручную** — договорная цена после торга часто отличается от сметы. Если сумму не вводить, раздел работает, просто не показывает строку «осталось получить».

## 3. Как это выглядит (мобильный, 320–412 px)

В хабе объекта плитка **«Faktury i zaliczki»** (справа число «Do otrzymania: N zł», если задана договорная сумма). Внутри — **сверху сводка**, ниже **три вкладки**:

* **Сводка:** Umówiona kwota · Zafakturowano · Otrzymano od klienta · Do otrzymania · Wydatki na materiały · Wynik (otrzymano − wydatki). Все числа считает **сервер**.
* **«Od klienta»** (деньги, которые вы взяли у клиента): виды **Zaliczka** (аванс) и **Wpłata** (оплата). Поля: сумма, дата, **«за что»**, необязательно: к какой фактуре относится, заметка.
* **«Faktury»** (выставленные клиенту): номер, сумма, дата, срок оплаты, **«за что»**; статус «оплачена / частично / просрочена» вычисляется по привязанным оплатам и сроку. Фото фактуры можно приложить.
* **«Materiały»** (ваши расходы): что куплено («за что»), где (**Sklep / dostawca**), сумма, дата, вид документа **paragon (чек) / faktura**, **фото чека / фактуры** (несколько). Необязательно: нетто и VAT «для справки».

Формы: широкие кнопки, сумма — `inputMode="decimal"`, дата по умолчанию «сегодня», редкие поля спрятаны за «Opcje», подсказки-заготовки для «за что» (из словаря PL / RU, свободный текст остаётся). Длинные тексты переносятся; цели касания ≥ 44 px; всё проверяется на 320 / 390 / 412 в PL и RU.

## 4. Модель данных (одна обратимая миграция на запись данных + одна на фото; только создание)

**`project_payments`** — одна запись расчётов:

| Поле | Тип | Заметки |
|---|---|---|
| `id` | UUID | можно создать на телефоне (работа без связи) |
| `owner_id`, `project_id` | UUID FK | `project_id` → `ON DELETE CASCADE`: запись уходит вместе с объектом (AC-5b: в сводке удаления строка «Wpisy rozliczeń: N») |
| `kind` | `INVOICE` / `ADVANCE` / `PAYMENT` / `EXPENSE` | CHECK |
| `title` | String(500) NOT NULL | **за что** |
| `number` | String(64) NULL | номер фактуры / документа |
| `amount_gross` | Numeric(12,2) > 0 | PLN |
| `amount_net`, `vat_rate` | Numeric NULL | справочно |
| `occurred_on` | Date | дата выставления / получения / покупки |
| `due_on` | Date NULL | срок оплаты (для фактуры) |
| `settles_id` | UUID NULL, FK на себя `SET NULL` | оплата → какую фактуру гасит |
| `counterparty` | String(255) NULL | магазин / поставщик (для `EXPENSE`) |
| `document_kind` | `RECEIPT` / `INVOICE` NULL | для `EXPENSE`: чек или фактура |
| `note` | Text NULL | |
| `is_archived` | bool | архив вместо удаления (учёт) |
| `created_at`, `updated_at` | UTC | |

**`project_finance`** — по одной необязательной записи на объект: `project_id` (PK, FK `CASCADE`), `agreed_amount` Numeric(12,2) NULL (договорная сумма), `currency` ('PLN'), `updated_at`.

**Фото чеков и фактур** (миграция следующего шага): новый **контекст вложения `PAYMENT`** и колонка `photo_attachments.payment_id` (FK на `project_payments`, `ON DELETE RESTRICT`, как у остальных целей); CHECK контекстов расширяется. Работают **те же** загрузка, просмотр, подписи, архив и корзина фото; фото записей расчётов видны и в общем «Archiwum → Zdjęcia» (подпись «объект → Rozliczenia → запись»). Удаление объекта (AC-5b) удаляет их вместе со всеми фото объекта (служба удаляет вложения по идентификаторам файлов).

Итоги (сервер): `agreed` (введённая или подсказка из сметы с указанием, из какой версии сметы), `invoiced` = Σ INVOICE, `received` = Σ (ADVANCE + PAYMENT), `to_receive` = `agreed` − `received` (если задано), `expenses` = Σ EXPENSE, `result` = `received` − `expenses` (кассовый результат; не прибыль в бухгалтерском смысле). Деньги — `Decimal`, округление только на сервере.

## 5. API

`GET /api/projects/{id}/payments?kind=` (+ итоги), `POST`, `PATCH`, `POST …/archive`, `POST …/restore`; `GET/PUT /api/projects/{id}/finance` (договорная сумма + подсказка из сметы); фото — существующий маршрут загрузки с контекстом `PAYMENT` и `payment_id`. Pydantic-схемы, изоляция по владельцу, структурированные ошибки.

## 6. Связи с уже сделанным

* **Stage 19 (без связи):** записи расчётов — в очередь (создание / правка / архив, идентификаторы с телефона); **фото чеков** — в очередь фото (19D), добавляется контекст. Сверка после возврата связи покрывается тестами.
* **Stage 18 (календарь):** срок оплаты фактуры → напоминание (событие `PAYMENT_TERM` уже есть) — отдельный шаг.
* **AC-5b (удаление объекта):** каскад + строка в сводке; расчёты **не держат** удаление (не документы клиента), но в сводке видно, что они уйдут.
* **Шифрование (`docs/CLIENT_DATA_ENCRYPTION_PLAN_RU.md`):** текстовые поля (`title`, `number`, `counterparty`, `note`) помечаются как шифруемые при V1; суммы и даты открыты (нужны серверу для итогов). Таблица проектируется так, чтобы это не требовало переделки.
* **Бэкап:** таблица попадает в дамп сама; миграции — после свежего backup A9 и ворот M.

## 9. Риски

* **Не бухгалтерия:** в интерфейсе подпись «реестр для справки, не фактура» (из словаря, не из кода).
* **Деньги — Decimal;** никакой арифметики во frontend; итоги с сервера.
* **Фото:** новая цель вложения затрагивает конвейер фото (ограничения, подсчёты, архив / корзина / удаление, очередь без связи): поэтому она вынесена в отдельный шаг IA-3 с собственными тестами и мутациями.
* **Объём:** IA-1 … IA-4 — четыре небольших релиза.
