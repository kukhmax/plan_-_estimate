# План: «Faktury i zaliczki» — фактуры, авансы и оплаты по объекту

Статус: **план v1 (2026-10-17), код не писался.** Это бэклог-пункт, **не этап дорожной карты** (нумерация Stage 0–20 не меняется; перенос в этап или новая нумерация — только по решению владельца, см. вопрос Q9). Каждый шаг ниже начинается только по явному «да» владельца.

## 1. Что просит владелец (2026-10-17)

В хабе объекта (экран «Смета / Помещения / Фото объекта / PDF-документы / Договор и протоколы / Резюме объекта …») добавить пункт **«Faktury i zaliczki»**: записывать **фактуры**, **взятые деньги** (авансы) и **оплаты** — с описанием, за что.

Как я это понимаю: это **внутренний реестр расчётов по объекту** (журнал для подрядчика), а не бухгалтерская система и не выставление документов клиенту. Он отвечает на вопросы: «что я выставил клиенту», «сколько уже получил и за что», «сколько осталось получить».

**Чего этот план сознательно НЕ делает** (и почему): не выставляет фактуры с точки зрения закона (нумерация, VAT, JPK, **KSeF** — обязательный национальный e-фактурный контур в Польше; это отдельный регулируемый продукт, ошибка там — штрафы). Приложение **записывает** номер и сумму фактуры, которую вы выставили в своей бухгалтерской программе.

## 2. Вопросы владельцу (с рекомендациями)

| № | Вопрос | Рекомендация |
|---|---|---|
| Q1 | Приложение только **записывает** фактуры или должно их **выставлять**? | Только записывать (реестр). Выставление / KSeF — вне MVP. |
| Q2 | Какие виды записей? | **Faktura** (выставлена клиенту), **Zaliczka** (взят аванс), **Wpłata** (получена оплата: по фактуре или просто). «Взятые деньги» я понимаю как **деньги, которые вы получили от клиента**. Если вы имели в виду ещё и **свои расходы** (закупка материалов по фактурам на вас) — это четвёртый вид **Wydatek**; рекомендую отдельным шагом после первых трёх. |
| Q3 | Суммы: брутто / нетто / VAT? | Обязательна **сумма брутто** (PLN). Нетто и ставка VAT — необязательные «для справки». |
| Q4 | К чему привязывать? | К **объекту** (всегда). Оплата — необязательно к **конкретной фактуре**. К договору / этапу — позже. |
| Q5 | Откуда «договорная сумма» для итога «осталось получить»? | Ручное поле «Umówione wynagrodzenie» в этом разделе (с подсказкой суммы принятой сметы, если она есть). Автоматически из договора не берём, пока договор не хранит сумму как число. |
| Q6 | Прикладывать скан / фото фактуры? | Да, **фото** (готовый конвейер фото; потребуется новый контекст вложения — миграция); PDF-файлы — позже. Первый шаг без вложений. |
| Q7 | Можно ли **удалить** запись? | Нельзя «просто стереть» (это учёт). **Архив / восстановить** + «сторно» (исправляющая запись); окончательно записи исчезают только вместе с объектом (AC-5b). |
| Q8 | Работа без связи (Stage 19)? | Да, как заметки: записать оплату на месте без сигнала. |
| Q9 | Где это в дорожной карте? | Предлагаю **бэклог-пункт** (как архивная чистка). Если вы хотите включить в **Stage 16 «Договоры»** (там уже есть аванс по договору, § 6) — скажите, я не меняю нумерацию без вашего решения. |
| Q10 | Показывать ли это клиенту (PDF «Rozliczenie»)? | Позже, отдельным шагом (клиентские документы — на польском, как остальные). |

## 3. Модель данных (проект; одна обратимая миграция, только создание)

Таблица `project_payments` (кошельковая запись объекта):

| Поле | Тип | Заметки |
|---|---|---|
| `id` | UUID | можно создать на телефоне (для работы без связи) |
| `owner_id`, `project_id` | UUID FK | `project_id` → `ON DELETE CASCADE` (запись уходит вместе с объектом, AC-5b: в сводке «Wpisy rozliczeń: N») |
| `kind` | `INVOICE` / `ADVANCE` / `PAYMENT` (позже `EXPENSE`) | CHECK |
| `title` | String(500), NOT NULL | **за что** (описание) |
| `number` | String(64), NULL | номер фактуры; для аванса / оплаты — номер документа, если есть |
| `amount_gross` | Numeric(12,2), > 0 | PLN |
| `amount_net`, `vat_rate` | Numeric, NULL | справочно |
| `occurred_on` | Date | дата выставления / получения |
| `due_on` | Date, NULL | срок оплаты (для фактуры) |
| `settles_id` | UUID, NULL, FK на `project_payments` `SET NULL` | оплата → фактура, которую она гасит |
| `note` | Text, NULL | |
| `is_archived` | bool | архив вместо удаления |
| `created_at`, `updated_at` | UTC | |

Итоги считает **сервер** (деньги — не во frontend, правило проекта): «Umówione», «Zafakturowane» (сумма фактур), «Otrzymane» (авансы + оплаты), «Do zapłaty» (= договорное − получено), статус фактуры «оплачена / частично / просрочена» (по привязанным оплатам и `due_on`).

## 4. API и экран

* `GET /api/projects/{id}/payments` (+ итоги), `POST`, `PATCH`, `POST …/archive`, `POST …/restore`; Pydantic-схемы; изоляция по владельцу; коды ошибок как в остальных маршрутах.
* **Хаб объекта:** плитка «Faktury i zaliczki» со значком «Do zapłaty: N zł» (или числом записей).
* **Экран (мобильный первым, 320–412 px):** сверху карточка итогов (4 строки), чипы-фильтры «Wszystko / Faktury / Zaliczki / Wpłaty», список карточек (дата, вид, номер, сумма, описание с переносом), широкая кнопка «Dodaj». **Форма:** вид (чипы), сумма (`inputMode="decimal"`), дата (сегодня по умолчанию), «За что» (подсказки-заготовки, но свободный текст), номер; «Opcje» (нетто, VAT, срок, к какой фактуре, заметка). Крупные цели касания (≥ 44 px), нет горизонтальной прокрутки, длинные русские подписи проверяются на 320 / 390 / 412.
* Тексты PL / RU в словарях; деньги форматирует общая утилита (никаких формул в компонентах).

## 5. Связи с уже сделанным

* **Stage 19 (без связи):** новые виды записей добавляются в правила очереди (создание / изменение / архив), с идентификаторами с телефона; тесты на сверку после возврата связи.
* **Stage 18 (календарь):** срок оплаты фактуры → напоминание (событие `PAYMENT_TERM` уже есть для аванса по договору) — отдельный шаг.
* **AC-5b (удаление объекта):** записи уходят каскадом; в сводке удаления добавляется строка; на удаление **не** влияют (не «держат»), но предупреждение «есть неоплаченные фактуры» — обсуждаемо.
* **Шифрование данных клиента** (`docs/CLIENT_DATA_ENCRYPTION_PLAN_RU.md`): суммы и описания расчётов — финансовые данные клиента; решение о шифровании этого раздела принимается там, и модель выше не мешает (поля описаний — текстовые).
* **Бэкап:** новая таблица попадает в дамп автоматически; миграция — после свежего backup A9 и ворот M, как в прошлых релизах.

## 7. Риски

* **Юридический / налоговый:** приложение не заменяет бухгалтерию и не ведёт VAT; в интерфейсе подпись «реестр для справки, не фактура» (через словарь, не в коде).
* **Деньги в Decimal, не в float;** округление только на сервере.
* **Двойной учёт:** оплата и фактура — разные записи; без привязки итоги всё равно сходятся (получено − договорное).
* **Объём:** IA-1 … IA-3 — три небольших релиза; IA-5 / IA-6 — только по необходимости.
