# Шифрование данных клиентов, шаг EN-2b-1 — перекодировка старых значений и строгое чтение

Статус: **EN-2b-1 готов локально (2026-10-18), не выложен.** Бэклог-пункт, **не этап дорожной карты**. Предыдущий шаг: `docs/CLIENT_ENCRYPTION_EN2A_RUNBOOK_RU.md` (EN-2a принят владельцем).

## 1. Зачем и что меняется

* После EN-2a **новые и изменённые** значения пишутся шифртекстом, а всё, что было записано раньше, остаётся открытым текстом в базе, в дампе и в бэкапах. Этот шаг превращает **старые** значения клиентов, объектов, представителей и заметок в шифртекст — **только после него шифрование защищает от утечки базы или дампа полностью.**
* **Строгое чтение** (`DATA_STRICT_READ=true`): открытое значение в зашифрованной колонке отклоняется (`DATA_PLAIN_VALUE_REFUSED`). Это страховка: если команда что-то пропустила или кто-то записал значение мимо приложения, вы узнаёте сразу, а не через год.
* **Документы** (снимки, HTML, названия в журнале) и **расчёты** этим шагом **не** затрагиваются: EN-2b-2 и EN-2b-3, каждый со своей выкладкой и вашим «да».
* Миграций нет, зависимостей нет, frontend не меняется. Пересоздаётся только backend.

## 2. Команда перекодировки

`docker exec plan_estimate_backend python -m app.cli.reencode_data <команда>` (внутри контейнера backend; выводит **только числа**, никогда значения или ключи):

| Команда | Что делает |
|---|---|
| `report` | только чтение: по каждой колонке — сколько значений хранится, сколько уже шифртекст, сколько открытых |
| `verify` | только чтение: `report` + **расшифровывается каждый шифртекст** (неверный ключ, повреждённое или перенесённое значение считаются) |
| `apply [--limit N] [--batch-size N]` | заменяет открытые значения шифртекстом; повторяема и возобновляема |

* Колонки берутся **из самих моделей** (все колонки типа `EncryptedText`, сейчас 20: клиенты 11, объекты 5, представители 3, заметки 1), поэтому колонка, добавленная позже, подхватывается без правки команды.
* Порции по 200 значений, **каждая — своя транзакция**. Можно остановить (Ctrl+C) и запустить снова.
* **Значение заменяется, только если оно всё ещё то, что было прочитано** (сравнение и замена одним оператором). Если вы сохранили запись, пока команда работала, это значение пропускается (код выхода 5) и подхватывается повторным запуском; ваша правка не затирается.
* «Дата изменения» (`updated_at`) записей **не меняется**: перекодировка — не правка.
* Каждый владелец получает шифртекст **своим** ключом данных.
* Коды выхода: `0` готово (для `verify` — открытых и нерасшифровываемых нет), `2` неверные параметры, `3` открытые или нерасшифровываемые значения остались, `4` не настроен `DATA_KEK`, `5` часть значений пропущена, потому что изменилась.

## 3. Порядок выкладки

1. Свежий бэкап A9 под текущую голову (не старше суток): `cd ~/apps/plan_-_estimate && BACKUP_BRANCH=backlog-client-encryption BACKUP_HEAD=0062_data_keys bash ~/backup_a9.sh` (в **новой** SSH-сессии, потом закрыть её).
2. Запуск скрипта (в **новой** сессии):
   `cd ~/apps/plan_-_estimate && git fetch -q origin backlog-client-encryption && git show origin/backlog-client-encryption:docs/CLIENT_ENCRYPTION_EN2B1_DEPLOY_RU.sh > ~/deploy_en2b1.sh && bash ~/deploy_en2b1.sh`
3. Ворота **B**: `ВЫКЛАДКА ДА` — пересоздаётся backend (30–60 секунд), данные не меняются. Скрипт покажет `report`.
4. Ворота **R**: `ПЕРЕКОДИРОВКА ДА` — старые значения становятся шифртекстом; скрипт сам запускает `apply` (до трёх попыток) и затем `verify`: открытых значений 0, нерасшифровываемых 0, число строк то же.
5. Ворота **S**: `СТРОГОЕ ЧТЕНИЕ ДА` — в `.env.production` ставится `DATA_STRICT_READ=true`, backend пересоздаётся; скрипт читает **все** строки через приложение в строгом режиме и сверяет число строк с базой.
6. После `ВСЁ PASS`: чек-лист EN-2a (раздел 4 runbook EN-2a), затем бэкап под текущую голову `BACKUP_BRANCH=backlog-client-encryption BACKUP_HEAD=0062_data_keys bash ~/backup_a9.sh` (теперь в нём шифртекст).

## 4. Откат — порядок и предел

* **До ворот R** (данные не менялись): образ `pre-en2b1` и `up --no-deps --no-build backend` (команда в сообщении скрипта).
* **После перекодировки** образ **до EN-2a** (без шифрования) данные **не прочитает**. Запасной образ — EN-2a: он читает шифртекст. Бэкап A9 до перекодировки хранит открытые значения (он зашифрован age и лежит отдельно).
* **Строгое чтение** выключается без потери данных: `DATA_STRICT_READ=false` в `.env.production` и `docker compose ... up -d --no-deps backend`.
* **Ключ `DATA_KEK` по-прежнему нельзя терять и менять** (ротация — шаг EN-3).

## 5. Что остаётся открытым после этого шага (честно)

* **Документы:** снимки и HTML выданных договоров и протоколов, название в журнале отправленных — до EN-2b-2.
* **Расчёты** («Faktury i zaliczki»: название, номер, контрагент, примечание) — до EN-2b-3.
* **Прежние бэкапы** хранят то, что было в базе в момент бэкапа (открытые значения до перекодировки); они зашифрованы age (на сервере лежит только публичный ключ получателя). Бэкапы после этой выкладки содержат шифртекст.
* **Фото** клиентов не шифруются (решение EN-6).

## 6. Что проверено

* `backend/tests/test_en2b1_reencode.py` (16): список колонок из моделей; `report` ничего не меняет; `apply` шифрует все значения, чтение не меняется, `updated_at` не двигается, повтор ничего не делает, остановка и возобновление, пропуск изменившегося значения, ключ каждого владельца, пустая строка, `verify` считает испорченные, без ключа ничего не делается; строгое чтение отклоняет открытое значение и принимает перекодированное, не трогает пустые значения и не действует при выключенном шифровании; команда печатает только числа и все коды выхода.
* PostgreSQL 16 с настоящей командой (подпроцесс): 450 открытых клиентов + объекты, представители, заметки; `apply --limit`, повтор, сохранение владельцем во время перекодировки, второй `apply` ничего не меняет, `verify`, неверный ключ, строгое чтение, открытое значение «мимо приложения» отклоняется и находится `verify`: все проверки PASS.
* Мутационная проверка: 17 из 18 искусственных поломок ловятся (одна — избыточная защита).
* Скрипт выкладки на заглушках: полный проход, повтор после пропуска, готовая строка `DATA_STRICT_READ=false`; 16 отказов (фразы, ключ, бэкап, ключи данных, строгое чтение уже включено, перекодировка не доведена, нерасшифровываемое, чтение в строгом режиме, пять недопустимых изменений релиза).
