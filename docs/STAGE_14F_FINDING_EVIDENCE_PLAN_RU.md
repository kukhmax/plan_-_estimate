**Основание:** `docs/STAGE_14_PHOTO_FIXATION_ARCHITECTURE.md` §6, §15.5, §19 (решения D14-26 / OD-5 / OD-11 утверждены владельцем);
`docs/STAGE_14C_MEDIA_API_CONTRACT.md` (схема `photo_attachments` уже содержит `inspection_id`, `question_id`, `finding_id`, CHECK и уникальные индексы
для контекстов INSPECTION и FINDING; API сейчас отвечает `422 PHOTO_CONTEXT_NOT_SUPPORTED`).
**Не входит в 14F:** точки на фото (14G), фото выполнения работ (14H), отчёт (14I / Stage 15).

## Что такое «линия» замечания

Замечание (`InspectionFinding`) создаётся при завершении осмотра. Если замечание исчезло (resolved) и при повторном завершении подтвердилось снова,
Stage 6 создаёт **новую строку** с новым UUID (от UUID зависят подписи Stage 7 / 11, оживлять строку нельзя). Чтобы фото, снятые на прежней строке,
оставались с замечанием, строки одного источника `(inspection_id, question_id, finding_key)` получают общий **`lineage_id`**. Фото остаются
привязаны к той строке, на которой сняты (`finding_id`); чтение и отчёты группируют по `lineage_id`.

## Критерии PASS (14F.1)

- Миграция обратима (up / down / up), единственный head, DDL для PostgreSQL проверен; backfill детерминирован и не меняет ни UUID замечаний, ни флаги, ни даты.
- Resolve → повторное подтверждение: новая строка с новым UUID и прежним `lineage_id`; активные замечания сохраняют и UUID, и lineage; разные источники / осмотры — разные линии.
- Полный backend-набор: без новых падений; Stage 7 / 11 не затронуты.
