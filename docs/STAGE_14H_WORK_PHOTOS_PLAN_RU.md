Статус: **план 2026-10-07, старт одобрен владельцем («начинаем 14H»)**. 14H.1 (API) выполнен и запушен (`bed5b43`), 14H.2 (интерфейс Realizacja) выполнен локально 2026-10-07, 14H.3 (выкладка и проверка владельцем) впереди. Архитектура утверждена ранее: `docs/STAGE_14_PHOTO_FIXATION_ARCHITECTURE.md` §7, §19 (14H), решения D14-12 … D14-16, D14-24. Контракт API: `docs/STAGE_14C_MEDIA_API_CONTRACT.md` (§29 появится в 14H.1).

## 1. Что уже есть

- Схема `0032` содержит всё для WORK: значение `WORK` в enum, колонки `surface_id`, `occurrence_key` (без FK), `price_item_id`, ветку CHECK и частичный уникальный индекс `uq_photo_att_work_active (asset_id, surface_id, occurrence_key)`. **Миграции не нужно.**
- Stage 13: `occurrence_key` — долговечный идентификатор работы в плане поверхности; `SurfaceWorkExecution` создаётся лениво (NOT_STARTED = нет строки); работа без ключа в плане = «оторванная» (detached) и остаётся историей.
- 14C/14E/14F: загрузка, очередь, фото-секция, счётчики, просмотрщик — уже работают для PROJECT / ROOM / SURFACE / OPENING / INSPECTION / FINDING. WORK сейчас отклоняется (`422 PHOTO_CONTEXT_NOT_SUPPORTED`).

## 2. Правила (из утверждённой архитектуры)

1. Идентичность WORK-фото = **поверхность + `occurrence_key`** + снимок `price_item_id` (чтобы оторванная работа осталась подписанной). `SurfacePlannedWork.id` не используется никогда.
2. Фото «ДО» **не требует** строки выполнения (NOT_STARTED).
3. Новое WORK-вложение принимается **только для ключа, который сейчас есть в плане этой поверхности**, иначе 409 (без утечки чужих данных). `price_item_id` клиент **не присылает**: сервер берёт его из текущей работы плана.
4. Существующие фото не трогаются правками плана: APPEND и «применить ко всем» **не копируют** фото; REPLACE и удаление работы **не удаляют** фото (остаются как доказательство оторванной работы и попадают в отчёт); повторное добавление той же позиции прайса = новый ключ, **старых фото не наследует** (сопоставление только по ключу).
5. Завершение работы **никогда не требует** фото. Категория предлагается по статусу (NOT_STARTED → BEFORE, IN_PROGRESS → IN_PROGRESS, COMPLETED → AFTER), её можно изменить.
6. Фото выполнения — это доказательства выполнения, как фото осмотра: **живут в Realizacja** и не попадают в общий список объекта и в суммы помещений (`site_only` их не содержит).

## 3. Подэтапы

### 14H.1 — API (backend, без миграции)
- `PhotoAttachmentService`: контекст `WORK` (обязательные `surface_id` + `occurrence_key`, остальные цели запрещены); цепочка поверхность → помещение → проект → владелец; ключ должен быть текущим в плане этой поверхности (новое исключение → `409 WORK_OCCURRENCE_NOT_CURRENT`); `price_item_id` снимается с работы плана; дубликаты по `(asset, surface, occurrence_key)`.
- Загрузка (`POST /photos`): поле `occurrence_key` (форма WORK — `upload_id`, `context`, `surface_id`, `occurrence_key`, `category`, `caption`, `include_in_report`, `source` = ровно 8 полей, **лимит 8 не меняется**); «прикрепить существующее»: поле в запросе; `PhotoAttachmentRead` отдаёт `occurrence_key` и `price_item_id`.
- Чтение: список с `context=WORK&surface_id=…` (все WORK-фото поверхности, включая оторванные) и фильтр `occurrence_key`; `site_only` исключает WORK; счётчики `/photos/counts` получают `works` (по ключу) и `work_surfaces` (по поверхности) — вне `rooms` и `room_totals`.
- Тесты: matrix форм, цепочка владельца, текущий / не текущий / чужой ключ, BEFORE без строки выполнения, APPEND / «применить ко всем» / REPLACE / удаление / повторное добавление, дубликаты, фильтры, `site_only`, счётчики, курсор, совместимость остальных контекстов.

### 14H.2 — интерфейс Realizacja (frontend)
- В **карточке каждой работы** (`SurfaceExecutionView`) — кнопка фото со счётчиком (≥ 44 px), панель сворачивается; загрузка и камера как в 14F; категория по умолчанию из статуса, меняется в «Opcje».
- Блок **«Фото прежних работ»** в конце Realizacja: WORK-фото этой поверхности, ключа которых больше нет в плане, с подписью снимка работы.
- Счётчики и хуки (`usePhotoCounts`, `ProjectPhotosContext`) знают про `works` / `work_surfaces`; PL / RU; мобильные правила (320 / 390 / 412 px, переносы, без горизонтальной прокрутки).
- Тесты: vitest (поведение, мутационные проверки), tsc, build; реальный Chromium на 320 / 390 / 412 px, PL / RU.

### 14H.3 — выкладка и проверка владельцем
- Короткий runbook (без миграции): бэкап не обязателен (схема не меняется), сборка backend + frontend, пересоздание, проверка подписанной ссылки **с чужого адреса** (A8-0 из 14F.4), проверка на телефоне.
