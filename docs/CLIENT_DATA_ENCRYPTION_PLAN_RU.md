# План: шифрование данных клиентов — «читает только Mini App владельца»

Статус: **план v1 (2026-10-17), код не писался, production не затронут.** Бэклог-пункт, **не этап дорожной карты**; нумерация Stage 0–20 не меняется. Это решение с последствиями для всей архитектуры, поэтому в плане сначала **модель угроз и честные ограничения**, потом варианты, потом шаги; **первый шаг — проверка на вашем телефоне (spike)**, а не код.

## 1. Что просит владелец

Хранить данные клиентов на сервере так, чтобы **их мог прочитать только Mini App владельца**: придумать ключи расшифровки, доступные только на аккаунте Telegram владельца.

## 2. Честная модель угроз (от кого защищаем)

| Угроза | Сегодня | Что даёт шифрование |
|---|---|---|
| **T1.** Утечка дампа БД / бэкапа / снимка диска (украденный файл) | бэкапы A9 уже **зашифрованы** (Stage 14D); база на диске VM — нет (диск шифруется самой Oracle по умолчанию, это не защита от доступа в работающей системе) | **основной выигрыш** любого варианта ниже |
| **T2.** Взлом работающего сервера (злоумышленник в контейнере backend) | видит всё | только вариант с ключом владельца **не при каждом запросе** помогает; пока ключ в памяти процесса, взломщик его может взять |
| **T3.** Администратор сервера / хостинг (вы сами, Oracle) | видит всё | вариант «ключ только у владельца» убирает доступ «по умолчанию» |
| **T4.** Разработчик / инструменты на этапе разработки | я работаю в песочнице, к данным production не обращаюсь (SSH и данные — только у вас) | не меняется |
| **T5.** Потеря телефона / захват аккаунта Telegram | доступ ко всему, как у владельца | ключ на устройстве + блокировка / биометрия снижают риск; ключ в облаке Telegram — нет |
| **T6.** Сам Telegram | видит чаты бота, отправленные PDF | не решается |

**Что должно быть правдой в любом решении:** сервер сегодня **сам использует** данные клиента — собирает PDF (WeasyPrint на сервере), отправляет документы ботом в Telegram, отправляет напоминания календаря от своего имени (владелец может быть не в сети), ищет клиентов по имени / телефону, проверяет NIP / индекс. Чем «тверже» шифрование, тем больше из этого ломается (раздел 4).

## 3. Что считается «данными клиента» (инвентаризация по моделям)

* **Клиент:** имя, фамилия, название фирмы, телефон, e-mail, NIP, улица, индекс, город, Telegram, заметки.
* **Объект:** название, адрес, город, индекс, описание; **представители** (имя, телефон, e-mail); **заметки объекта**.
* **Документы:** ответы договора, **снимки и HTML выданных документов** (договор, протоколы передачи / скрытых работ / решений / приёмки / простоя) — в них полные данные клиента.
* **Расчёты** (`docs/INVOICES_ADVANCES_PLAN_RU.md`, когда появятся): описания и суммы.
* **Фото:** снимки домов клиентов в R2 (файлы).
* **Не относится к персональным данным клиента** (шифровать не надо): идентификаторы, статусы, даты, структура помещений / поверхностей и размеры, позиции прайса, коэффициенты, расчёты площадей и смет в виде чисел.

## 4. Что ломается, если ключ есть только у владельца

| Функция | Влияние при «ключ только в Mini App» |
|---|---|
| PDF договоров / протоколов / смет / фото-отчёта | сервер собирает PDF → ему нужны данные клиента в открытом виде **на время сборки**; при чистом E2E пришлось бы собирать PDF на телефоне — это переписывание конвейера документов (Stage 15–16) |
| Отправка документа ботом в Telegram | то же: файл создаёт сервер |
| Напоминания календаря (Stage 18) | сервер шлёт тексты без участия владельца: тексты с именем клиента невозможны; нужны нейтральные («Объект 3») |
| Поиск клиентов по имени / телефону, сортировка | на сервере невозможны (нужен «слепой индекс» для точного поиска или поиск на телефоне по всему списку) |
| Проверка NIP / индекса | делается на телефоне до шифрования |
| Резервные копии A9 | дамп уже содержит шифртекст; **восстановить читаемо можно только с ключом** (это прямая цена) |
| Удаление AC-5, сводки «что будет удалено» | не зависят от содержимого (счётчики) |
| Работа без связи (Stage 19) | локальный кэш в IndexedDB сейчас **открытый**; при шифровании его тоже нужно шифровать |

## 5. Варианты

| Вариант | Суть | Защищает от | Цена |
|---|---|---|---|
| **V0** | Ничего не шифровать; только гигиена (минимизация данных, сроки хранения, журнал доступа, документ RODO) | — | малая |
| **V1. «Шифрование в покое ключом сервера»** | поля клиентов шифруются AES-256-GCM (оболочечное шифрование: ключ данных + мастер-ключ в переменных окружения / секрет-хранилище); сервер расшифровывает на лету | **T1** (дамп, диск, бэкап, утечка файла) | **небольшая**: все функции работают; поиск — через «слепые индексы» для телефона / NIP, по имени — ограниченно |
| **V2. «Ключ владельца, запечатанная модель»** | данные шифруются ключом, которого **нет на сервере в покое**; Mini App при входе передаёт серверу ключ **на время сессии** (в памяти процесса, не на диск); сервер расшифровывает «на лету» (PDF, ответы); без сессии данные недоступны | **T1, T3** (и частично T2: нужен захват **во время** сессии) | **средняя / высокая**: напоминания без имён; бот не может собрать документ вне сессии; потеря ключа = потеря данных клиентов; миграция существующих данных |
| **V3. Настоящий E2E** | ключ никогда не уходит с телефона; всё шифруется и показывается на телефоне; PDF собирается на телефоне | T1, T2, T3 | **очень высокая**: переписать документы, календарь, отправку, поиск; **не рекомендую для MVP** |

**Моя рекомендация:** идти **V1 → V2**. V1 закрывает самую реальную угрозу (утечка дампа) почти бесплатно и не ломает функции; V2 добавляется, если после V1 владелец хочет, чтобы даже администратор сервера не мог прочитать данные «просто так», и принимает цену (нейтральные напоминания, ответственность за ключ). V3 — нет.

## 6. Где хранить ключ владельца (для V2) — что известно и что проверить

**Нельзя** выводить ключ из Telegram `user_id` или из `initData`: `user_id` публичен, а `initData` может сформировать любой, у кого есть токен бота (у сервера он есть) — это не секрет владельца.

Варианты хранения секрета на стороне Mini App:

| Вариант | Свойства | Вопросы |
|---|---|---|
| **A. Случайный ключ, созданный в Mini App, в Telegram `SecureStorage`** (Bot API 9.0, апрель 2025: защищённое хранилище на устройстве; по описаниям — Keychain на iOS, Keystore на Android) | не покидает устройство; **не синхронизируется между устройствами**; `restoreItem` для восстановления на устройстве | поддерживается ли на вашем Telegram и Android; что происходит при переустановке / смене телефона |
| **B. Копия ключа в `CloudStorage`** (синхронизируется между устройствами; по сторонним источникам до 1024 значений на пользователя на бота), **обёрнутая парольной фразой** (PBKDF2 / Argon2 через WebCrypto) | новый телефон: ввести фразу | лимиты размера значений — проверить; Telegram хранит облачные данные на своих серверах (обёрнутый ключ без фразы бесполезен) |
| **C. Парольная фраза при каждом запуске** | ничего не хранится | неудобно «на стройке с телефоном в руке»; допустимо как запасной вариант |
| **D. Биометрия** (`BiometricManager` Mini Apps) для разблокировки ключа | быстро и безопасно | поддержка на устройстве — проверить |
| **E. Бумажная фраза восстановления** (24 слова / QR), выданная один раз | единственная защита от потери телефона | её нужно сохранить владельцу; **без неё и без ключа данные клиентов не восстановить** |

Криптография в Mini App: **WebCrypto API** (AES-GCM; `CryptoKey` неизвлекаемый, хранится в IndexedDB), деривация ключа — PBKDF2 (встроено) или Argon2 (WASM). Всё это проверяется на реальном Telegram владельца, а не по документации: **шаг EN-1 (spike).**

**Источники для проверки фактов (вторичные, к проверке на практике):** [Telegram Mini Apps (официальная страница)](https://core.telegram.org/bots/webapps), [DeviceStorage и SecureStorage (обзор)](https://pimenov.ai/knowledge/telegram-mini-apps-device-storage-secure-storage/). Официальная страница из песочницы разработки недоступна (сетевой доступ ограничен), поэтому пределы и поведение берутся в spike, а не из моей памяти.

## 7. Юридический контекст (RODO / GDPR) — не юридическая консультация

Шифрование — одна из рекомендуемых мер безопасности (ст. 32 RODO), но **не заменяет**: реестр операций обработки, цель и срок хранения, право на удаление (у нас теперь есть удаление клиента и объекта, AC-5), договор поручения, если данные хранит сторонний сервис. Проверка юристом — как и для базы знаний, отложена до решения владельца.

## 10. Риски

* **Потеря ключа = потеря данных** (V2): поэтому фраза восстановления и проверка восстановления из бэкапа с ключом — обязательные шаги.
* **Миграция существующих данных** необратима при ошибке в ключе: двойная запись, проверка на копии, backup A9 до, откат по инструкции.
* **Ложное чувство безопасности:** V1 не защищает от взлома работающего сервера; об этом написано здесь и должно быть написано владельцу.
* **Сложность:** V2 затрагивает документы, календарь, бот и поиск — делать только осознанно и малыми шагами.
