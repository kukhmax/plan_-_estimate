## 3. Принципы (из правил проекта)

1. **Данные → шаблон → PDF.** Шаблоны получают готовую модель (dataclass / dict), считают ничего: суммы, количества и порядок приходят из снимков (Stage 10) и сервиса 14I; цены и формулы не появляются ни в шаблонах, ни в интерфейсе.
2. **Документы для клиента — всегда на польском** (PL), независимо от языка интерфейса; интерфейс владельца — PL / RU. Все польские тексты — в backend (`app/domain/documents/locales/pl.json`), не в React.
3. **Юридический текст не пишется в этом этапе** (договоры, оговорки, цитаты норм — Stage 16 / 17). Каркас готовит только структуру: шапка, нумерация страниц, блок подписей, место под разделы.
4. **Детерминизм и повторяемость:** один и тот же снимок + версия шаблона → тот же документ (кроме даты формирования).
5. **Безопасность:** владелец → проект → документ (как везде, чужое → 404); в PDF и в журнал не попадают ключи хранилища, ссылки и данные другого владельца; ошибки — структурированный конверт, без `except: pass`.
6. **Ресурсы:** рендер в **отдельном процессе** (не в цикле событий API) с таймаутом и ограничением памяти, не более одного одновременно, лимиты числа фото и размера картинок (фото уменьшаются до размера печати).
7. **Мобильный интерфейс** (320–412 px, PL / RU): кнопки «Wyślij PDF» ≥ 44 px, понятные состояния «формируется / отправлено / ошибка».

## 4. Подэтапы

### 15B — движок документов (backend, без интерфейса)
- Зависимости (точные версии, `tests/test_dependency_pins.py`): Jinja2, WeasyPrint и его зависимости; для тестов — чтение PDF (`pypdf`). `backend/Dockerfile`: системные библиотеки и шрифт (DejaVu / Noto с польскими и русскими глифами), без роста образа сверх необходимого; сборка для production (ARM64) проверяется на выкладке.
- Пакет `app/domain/documents/`: `DocumentRenderer` (HTML → PDF в отдельном процессе с таймаутом и ограничением памяти, один одновременно), базовый шаблон (A4, поля, «Strona X z Y», номер и дата документа, блок исполнителя и клиента, блок подписей), форматирование PL (`1 234,50 zł`, `12,50 m²`, даты), польский словарь, реестр шаблонов с версией.
- Тесты: корректный PDF (`%PDF`, число страниц, текст читается, польские и русские буквы не теряются), таймаут и остановка процесса, лимиты, детерминизм структуры, отсутствие сети и обращений к хранилищу в шаблонах.
- Без миграции, без интерфейса, без выкладки (код едет вместе с 15F / 15H).

### 15C — профиль исполнителя (миграция, API, экран) — **реализовано локально 2026-10-08**
- **Данные:** одна запись на владельца (`owner_id` уникален, FK `users` с каскадом): название (фирма или ФИО, обязательно), NIP, улица, индекс, город, телефон, e-mail, расчётный счёт (всё, кроме названия, необязательно). Хранятся **канонические** значения: NIP — 10 цифр, индекс — `00-000`, счёт — 26 цифр (NRB), e-mail с нижним регистром домена, телефон — с пробелами нормализованными. Миграция `0037_executor_profiles` обратима; в БД — CHECK длины NIP / счёта и непустого названия.
- **Проверки (`app/domain/rules/polish_identifiers.py`):** контрольная сумма NIP (веса 6-5-7-2-3-4-5-6-7, mod 11), контрольная сумма NRB (mod 97), формат индекса, e-mail, телефон (≥ 7 цифр). Префикс `PL`, пробелы, дефисы и точки в NIP / счёте принимаются и убираются.
- **API:** `GET /api/executor-profile` → `{"profile": …|null}`; `PUT` — полная замена (не отправленные необязательные поля очищаются). Ошибки полей приходят **все сразу**: 422 `{"detail": {"code": "EXECUTOR_PROFILE_INVALID", "message": …, "fields": {поле: КОД}}}` (`NAME_REQUIRED`, `NIP_INVALID`, `POSTAL_CODE_INVALID`, `EMAIL_INVALID`, `PHONE_INVALID`, `BANK_ACCOUNT_INVALID`). Чужого профиля нет по построению: профиль всегда берётся по владельцу из токена. Лишние поля запрещены (`extra=forbid`).
- **Документы:** `party_from_executor_profile` собирает блок исполнителя для шапки (NIP с дефисами, адрес без пустых строк); текст экранируется шаблоном.
- **Экран:** кнопка «Profil wykonawcy / Профиль исполнителя» в окне «Konto» (не новая вкладка навигации), полноэкранный лист: загрузка / ошибка с повтором / сохранение, подписи полей, ошибки у каждого поля (тексты PL / RU по коду), `inputMode` numeric для NIP / индекса / счёта, поля 16 px и ≥ 44 px. BackButton Telegram закрывает сначала профиль, затем окно; пока окно открыто, BackButton рабочей области отключён.
- Выкладка — в 15H (миграция и пересборка образов бэкапа: голова меняется на `0037`).

### 15D — смета в PDF (Kosztorys)
- Модель документа из `FINAL`-сметы: заголовок, исполнитель, клиент, объект и адрес, таблица позиций (польские названия через словарь backend), количества, цены, суммы, итоги, примечания; `DRAFT` — только предпросмотр для владельца с пометкой «WERSJA ROBOCZA» (решить в 15D).
- Тесты: суммы равны снимку сметы, все ключи названий переведены (тест против `pl.json` frontend), порядок позиций, длинные названия, много страниц.
- **Решения владельца (2026-10-08):** (1) **без НДС**: в PDF только конечная цена для заказчика, одна колонка суммы, без netto / brutto; НДС владелец сделает отдельно позже (в 15D не моделируется, схему не усложняем); (2) **нумерация**: формат по дате и времени выпуска (`KOSZ/2026/10/08/1953`, Europe/Warsaw, при совпадении минуты суффикс `-2`), **плюс сквозной порядковый номер документов одного клиента и объекта** (1, 2, 3 …) — номер присваивается один раз при выпуске и не меняется; присвоение и счётчик живут в журнале выданных документов (15F), поэтому PDF сметы в 15D печатает номер из входных данных (до выпуска — без номера, «podgląd»); (3) **DRAFT-предпросмотр: да**, только владельцу, с пометкой «WERSJA ROBOCZA», клиенту не отправляется.
- Открытый вопрос к 15D: печатать ли коэффициенты (по умолчанию — нет, только итоговые суммы позиций).

### 15E — фотоотчёт осмотра в PDF
- Из сервиса 14I: по комнатам и поверхностям, фото с номерами; метки (кружки с номерами) и контуры поверх фото (SVG в долях картинки), подписи, легенда меток; находки по `lineage`; фото выполнения работ (если выбраны «в отчёт»).
- Ресурсы: уменьшение фото до печатного размера, лимит числа фото на документ, чтение байтов через порт хранилища (отображаемая копия, не оригинал), сообщение, если документ слишком велик.
- Тесты: метка и контур на нужном месте (проверка геометрии SVG), порядок как в 14I, архивные и не отобранные фото не попадают, лимиты, ошибка хранилища.

### 15F — выдача документа: журнал, бот, интерфейс
- Таблица «журнал выданных документов» (без файла): вид, источник (смета / отчёт), версия шаблона, статус (`QUEUED` / `RENDERING` / `SENT` / `FAILED`), размер, страницы, контрольная сумма, время; миграция.
- API: `POST /projects/{p}/documents` (вид и источник) → 202 и идентификатор; `GET` статуса; фоновая задача формирует PDF и отправляет его **ботом** (`sendDocument`) владельцу; зависшие `RENDERING` после перезапуска помечаются `FAILED`; повтор не создаёт дубль.
- Интерфейс: кнопки «Wyślij PDF» у сметы и у фото-отчёта объекта, индикатор состояния, понятные сообщения (бот не запущен, слишком большой документ, ошибка).
- Тесты, подмена Bot API; проверка на телефоне владельцем.

### 15G — каркас договоров и протоколов (без юридических текстов)
- Реестр видов документов (смета, фотоотчёт, договор, протокол передачи, протокол скрытых работ, итоговый протокол), версии шаблонов, нумерация (по решению владельца), общие блоки (шапка, подписи, приложения); пустые шаблоны-заготовки для Stage 16, проверка, что в них нет юридического текста.

### 15H — итоговая проверка и выкладка
- Состязательная проверка (как 14J): ограничения ресурсов на 1 OCPU, большие документы, русские / польские символы, матрица владельцев; сборка образа backend с новыми системными библиотеками, миграции `0037…` (+ журнал), пересборка образов бэкапа, выкладка с «да» на каждый шаг, проверка владельцем на телефоне (получить PDF сметы и фотоотчёта в чате и открыть).

## 4a. Результат 15B: как устроен движок (для следующих подэтапов)

Код: `backend/app/domain/documents/`. Как добавить документ (15D, 15E, 15G): 1) вид в `registry.DocumentKind` и запись `DocumentTemplate(kind, version, file)`; 2) шаблон `templates/<имя>.html.j2`, наследующий `_layout.html.j2` (блок `body`); 3) польские подписи — только в `locales/pl.json` (шаблон берёт их через `t('ключ')`; неизвестный ключ — ошибка, лишний ключ — ошибка теста); 4) данные — готовая модель (`DocumentLayout` с `DocumentMeta`, `Party`, плюс собственные поля шаблона), суммы и количества приходят из снимков, шаблон их только форматирует фильтрами `money`, `qty`, `area`, `percent`, `date`, `datetime`; 5) `render_html(template, context)` → HTML, `DocumentRenderer.render(html, assets)` → `RenderedPdf(pdf, pages, sha256, byte_size, render_seconds, worker_pid)`.

Гарантии движка (проверены тестами и мутациями):
| Тема | Как |
|---|---|
| Процесс | PDF делает отдельный процесс (`render_worker`), в своей группе процессов; один рендер за раз, второй ждёт `DOCUMENT_RENDER_WAIT_SECONDS`, потом `DocumentRenderBusyError` |
| Время и память | Таймаут `DOCUMENT_RENDER_TIMEOUT_SECONDS` (процесс убивается вместе с группой), лимиты адресного пространства (`DOCUMENT_RENDER_MEMORY_MB`), времени процессора и размера файла внутри процесса; отмена вызова тоже убивает процесс |
| Размеры | `DOCUMENT_MAX_HTML_BYTES`, `DOCUMENT_MAX_ASSETS`, `DOCUMENT_MAX_ASSET_BYTES`, `DOCUMENT_MAX_PAGES`, `DOCUMENT_MAX_PDF_BYTES` (меньше 50 МБ лимита Telegram), всё → `DocumentTooLargeError` |
| Ресурсы | Читаются только `data:`-адреса, встроенные шрифты и файлы самого документа (`assets/…`); `http`, `ftp`, чужие файлы и выход через `..` отклоняются двумя независимыми проверками; процесс получает минимальное окружение без секретов |
| Данные | Автоэкранирование (имя клиента с разметкой не ломает страницу), недостающее значение — ошибка, а не пустая строка; данные не попадают в таблицу стилей (колонтитул — «бегущий элемент» HTML) |
| Шрифт | DejaVu Sans (Regular, Bold) лежит в репозитории с лицензией, встраивается в PDF: польские буквы, кириллица (имена клиентов) и символы одинаковы на любом сервере; системные библиотеки и шрифт-запас ставит `backend/Dockerfile` |
| Форматирование | `1 234,50 zł`, `12,50 m²`, даты `дд.мм.гггг` по польскому времени; только `Decimal` / `int` / `str`, `float` отвергается; округление «half-up» |
| Остаток | Временная папка `pe-doc-*` удаляется при успехе, ошибке, таймауте и отмене |

Контрольная страница: вид `DIAGNOSTIC` (польские и русские буквы, символы, таблица с повторяющейся шапкой, номера страниц, подписи): ею проверяются шрифты и оформление на сервере.

## 5. Риски
| Риск | Мера |
|---|---|
| Образ backend вырастет, на ARM64 сборка и системные библиотеки могут отличаться от среды разработки | Сборка и проверка в 15H (A4 с откатным тегом); версии пакетов зафиксированы |
| Рендер большого отчёта перегружает 1 OCPU / 6 ГБ | Отдельный процесс, таймаут, лимит памяти, один одновременно, лимит фото и размера картинок |
| Названия позиций сметы хранятся как ключи перевода | Польский словарь на backend + тест покрытия; ключи без перевода — ошибка теста, а не пустая строка в PDF |
| Telegram `sendDocument` недоступен (бот заблокирован / не запущен) | Структурированная ошибка в интерфейсе; файл не теряется (создаётся заново) |
| Неверные суммы в документе | Суммы только из снимка сметы, никаких пересчётов в шаблоне; тест на равенство |

## 6. Открытые вопросы владельцу (задаются в момент нужного подэтапа)

4. **Лимит фото в отчёте (15E):** максимальное число фото на один PDF и что делать при превышении (несколько файлов или отказ).
5. **Логотип исполнителя:** в 15C не делаем; нужен ли позже.
