## 3. Принципы (из правил проекта)

1. **Данные → шаблон → PDF.** Шаблоны получают готовую модель (dataclass / dict), считают ничего: суммы, количества и порядок приходят из снимков (Stage 10) и сервиса 14I; цены и формулы не появляются ни в шаблонах, ни в интерфейсе.
2. **Документы для клиента — всегда на польском** (PL), независимо от языка интерфейса; интерфейс владельца — PL / RU. Все польские тексты — в backend (`app/domain/documents/locales/pl.json`), не в React.
3. **Юридический текст не пишется в этом этапе** (договоры, оговорки, цитаты норм — Stage 16 / 17). Каркас готовит только структуру: шапка, нумерация страниц, блок подписей, место под разделы.
4. **Детерминизм и повторяемость:** один и тот же снимок + версия шаблона → тот же документ (кроме даты формирования).
5. **Безопасность:** владелец → проект → документ (как везде, чужое → 404); в PDF и в журнал не попадают ключи хранилища, ссылки и данные другого владельца; ошибки — структурированный конверт, без `except: pass`.
6. **Ресурсы:** рендер в **отдельном процессе** (не в цикле событий API) с таймаутом и ограничением памяти, не более одного одновременно, лимиты числа фото и размера картинок (фото уменьшаются до размера печати).
7. **Мобильный интерфейс** (320–412 px, PL / RU): кнопки «Wyślij PDF» ≥ 44 px, понятные состояния «формируется / отправлено / ошибка».

## 4. Подэтапы

### 15B — движок документов (backend, без интерфейса)

- Пакет `app/domain/documents/`: `DocumentRenderer` (HTML → PDF в отдельном процессе с таймаутом и ограничением памяти, один одновременно), базовый шаблон (A4, поля, «Strona X z Y», номер и дата документа, блок исполнителя и клиента, блок подписей), форматирование PL (`1 234,50 zł`, `12,50 m²`, даты), польский словарь, реестр шаблонов с версией.
- Тесты: корректный PDF (`%PDF`, число страниц, текст читается, польские и русские буквы не теряются), таймаут и остановка процесса, лимиты, детерминизм структуры, отсутствие сети и обращений к хранилищу в шаблонах.
- Без миграции, без интерфейса, без выкладки (код едет вместе с 15F / 15H).

### 15C — профиль исполнителя (миграция, API, экран) — **реализовано локально 2026-10-08**
- **Данные:** одна запись на владельца (`owner_id` уникален, FK `users` с каскадом): название (фирма или ФИО, обязательно), NIP, улица, индекс, город, телефон, e-mail, расчётный счёт (всё, кроме названия, необязательно). Хранятся **канонические** значения: NIP — 10 цифр, индекс — `00-000`, счёт — 26 цифр (NRB), e-mail с нижним регистром домена, телефон — с пробелами нормализованными. Миграция `0037_executor_profiles` обратима; в БД — CHECK длины NIP / счёта и непустого названия.
- **Проверки (`app/domain/rules/polish_identifiers.py`):** контрольная сумма NIP (веса 6-5-7-2-3-4-5-6-7, mod 11), контрольная сумма NRB (mod 97), формат индекса, e-mail, телефон (≥ 7 цифр). Префикс `PL`, пробелы, дефисы и точки в NIP / счёте принимаются и убираются.
- **API:** `GET /api/executor-profile` → `{"profile": …|null}`; `PUT` — полная замена (не отправленные необязательные поля очищаются). Ошибки полей приходят **все сразу**: 422 `{"detail": {"code": "EXECUTOR_PROFILE_INVALID", "message": …, "fields": {поле: КОД}}}` (`NAME_REQUIRED`, `NIP_INVALID`, `POSTAL_CODE_INVALID`, `EMAIL_INVALID`, `PHONE_INVALID`, `BANK_ACCOUNT_INVALID`). Чужого профиля нет по построению: профиль всегда берётся по владельцу из токена. Лишние поля запрещены (`extra=forbid`).
- **Документы:** `party_from_executor_profile` собирает блок исполнителя для шапки (NIP с дефисами, адрес без пустых строк); текст экранируется шаблоном.
- **Экран:** кнопка «Profil wykonawcy / Профиль исполнителя» в окне «Konto» (не новая вкладка навигации), полноэкранный лист: загрузка / ошибка с повтором / сохранение, подписи полей, ошибки у каждого поля (тексты PL / RU по коду), `inputMode` numeric для NIP / индекса / счёта, поля 16 px и ≥ 44 px. BackButton Telegram закрывает сначала профиль, затем окно; пока окно открыто, BackButton рабочей области отключён.
- Выкладка — в 15H (миграция и пересборка образов бэкапа: голова меняется на `0037`).

### 15D — смета в PDF (Kosztorys) — **реализовано локально 2026-10-08**
- **Что печатается:** шапка (название, номер если есть, дата, место = город исполнителя), блоки «Wykonawca» (профиль 15C) и «Zamawiający» (клиент объекта), «Wersja N · название», блок «Obiekt» (название и адрес), таблица: Lp., описание (+ мелкая строка «поверхность · проём»), единица, количество (как в снимке: `12,50` или `18,345`, без округления), цена, стоимость; **группы по комнатам** в порядке первого появления (позиции без комнаты — «Pozycje ogólne»), «Razem — комната», общий «Razem». **Без НДС**, без коэффициентов (по решению владельца).
- **Данные только из снимка сметы:** ничего не пересчитывается. Проверки перед печатью (`DocumentDataError` со стабильным кодом): `ESTIMATE_ARCHIVED`, `ESTIMATE_EMPTY`, `ESTIMATE_CURRENCY_MIXED`, `ESTIMATE_UNPRICED` (для FINAL / ACCEPTED), `ESTIMATE_TOTAL_MISMATCH` (сумма позиций ≠ сохранённый итог), `EXECUTOR_PROFILE_REQUIRED` (для выданного документа), `DRAFT_NUMBERED`, `CATALOG_NAME_UNKNOWN`.
- **DRAFT-предпросмотр:** диагональный водяной знак «WERSJA ROBOCZA» на каждой странице, плашка «kosztorys nie został jeszcze zatwierdzony», без номера; строки без цены печатаются «do ustalenia», итог — «do ustalenia»; профиль исполнителя для предпросмотра не обязателен.
- **Польские названия:** встроенные позиции прайс-листа хранят ключ (`pricebook.seed.*`); бэкенд держит свой словарь `documents/catalog/price_names_pl.json` (49 ключей), тесты сверяют его с сидом (ни одного лишнего / пропущенного) и с `frontend/src/locales/pl.json` (тексты совпадают). Ключ без перевода — ошибка, а не сырой ключ в документе клиента. Названия владельца печатаются как есть.
- **Шаблон** `estimate.html.j2` версии `1` (в реестре `DocumentKind.ESTIMATE`), `EstimateDocumentService.build / html / render`; владелец проверяется сервисом смет (чужая смета или чужой объект → `EstimateNotFoundError`), клиент и профиль читаются только по владельцу.
- **Не входит (по плану):** выпуск, номер и журнал, отправка в чат, кнопки и HTTP-маршруты — 15F. Пример готового и черновика PDF отправлен владельцу на проверку вида.

### 15E — фотоотчёт осмотра в PDF — **реализовано локально 2026-10-08**
- **Что печатается:** шапка (исполнитель, клиент, объект), «Liczba zdjęć», далее по порядку модели 14I: «Zdjęcia ogólne obiektu» → комнаты → поверхности (с типом) → проёмы → работы (название позиции по-польски; убранные из плана помечены «poza aktualnym planem prac»; у фото работ — категория Przed / Po / …) → осмотры («Badanie podłoża — поверхность или sufit / podłoga, статус») → вопросы чек-листа (польский текст) → находки по `lineage` («Ustalenie: … — 12,50 mm / tak / текст», неактуальные приглушены). Фото по два в ряд с номером «Zdjęcie N» (сквозным), датой съёмки (иначе загрузки), подписью и легендой меток («Oznaczenia: 1 – …»).
- **Метки и контуры:** поверх фото рисуются кружки с номерами (красные, белая кайма) и контуры (белая подложка + красная линия) — по сохранённым долям картинки (0…1), в единицах напечатанной картинки, поэтому стоят там же, где на экране; размер кружка пропорционален ширине фото. Портретные фото печатаются уже (не выше 90 мм), чтобы не занимать страницу.
- **Фото для печати:** читается отображаемая копия (display, 2048 px) из хранилища; для страницы она уменьшается до 1000 px по длинной стороне, JPEG q=78 (≈ 100–150 КБ), без метаданных, с учётом ориентации; чтение по 4 одновременно, обработка по одному (1 ядро); временная папка всегда удаляется. Нечитаемое / недоступное фото = ошибка (`PHOTO_UNREADABLE`, `PHOTO_UNAVAILABLE`), а не молчаливая дыра в документе клиента.
- **Лимит 60 фото (решение владельца):** `DOCUMENT_MAX_PHOTOS`; проверяется **до чтения любого фото**; при превышении `PHOTO_LIMIT_EXCEEDED` с `details`: общее число, лимит, число фото общих и по каждой комнате — экран 15F предложит выпустить отчёт **по частям**: параметр `room_ids` (часть = выбранные комнаты, общие фото объекта — только если запрошены), в документе пометка «Raport częściowy — pomieszczenia: …». Пустой отчёт = `REPORT_EMPTY`.
- **Польские тексты чек-листа:** словарь `catalog/checklist_names_pl.json` (11 вопросов + 8 вариантов ответа) — тесты сверяют его с сидом шаблонов чек-листа и с `frontend/src/locales/pl.json`; ключ без перевода — ошибка.
- **Шаблон** `photo_report.html.j2` версии `1` (`DocumentKind.PHOTO_REPORT`), `PhotoReportDocumentService.prepare / build / html / render`; владелец проверяется моделью 14I (`ProjectNotFoundError` для чужого объекта), в отчёт попадают только фото «в отчёт» с обычной видимостью.
- **Не входит:** выпуск, номер, журнал, отправка в чат, кнопки и HTTP-маршруты — 15F. Примеры PDF показаны владельцу.

#### 15E.2 — рапорт осмотра: описания фото, ответы чек-листа и риски (**реализовано локально 2026-10-08**, по решению владельца)
Владелец принял: (1) строка места под каждым фото, (2) категория у любого фото кроме «Ogólne», (3) в легенде все метки (без подписи — «(bez opisu)»), (4) шапка осмотра с датой и статусом; и добавил: **ответы чек-листа и риски**, чтобы заказчик яснее видел картину и причины дополнительных работ.
- **Место:** под фото строка «Salon › Ściana A › Otwór: Okno» (для общих фото — название объекта; для осмотра — «Salon › Badanie podłoża — Ściana A», для находки — «… › Ustalenie: …»).
- **Блок осмотра** (после заголовка «Badanie podłoża — …»): Podłoże, Docelowy standard wykończenia (S1–S4 / Q1–Q4, если задан), Data zakończenia badania, Uwagi do badania; «Odpowiedzi z listy kontrolnej» по разделам (Tak / Nie, число с единицей, текст, выбранные варианты — только отвеченные вопросы); «Wykryte ryzyka» по убыванию тяжести: степень, название, пояснение, **Konsekwencje**, **Proponowane rozwiązanie**, при блокирующем риске — «Prace wykończeniowe w tym miejscu należy wstrzymać do usunięcia przyczyny».
- **Что в документ не попадает (сознательно):** текст `mitigation` (это указание подрядчику, а не клиенту — клиенту печатается готовая фраза `communication` от первого лица: «Wykonam wzmocnienie…»); признак «возможное ограничение ответственности / гарантии» (юридическая формулировка — Stage 17, протоколы); ответы и риски **черновика** осмотра (риски не вычислены, ответы могут меняться) и неактивные риски; заархивированные комнаты, поверхности и осмотры.
- **Структура:** новый read-only сервис `InspectionReportReadModel` (ответы, риски, поверхности, комнаты; число SQL-запросов не зависит от числа осмотров). Комната и осмотр без фото, но с ответами или рисками, **печатаются** (раньше такие узлы отбрасывались); пустой отчёт = нет ни фото, ни содержательных осмотров.
- **Польские тексты:** `catalog/risk_texts_pl.json` (15 правил × title / explanation / consequence / communication = 60 текстов), заголовки разделов чек-листа добавлены в `checklist_names_pl.json`; тесты сверяют их с сидом правил и шаблонов и с `frontend/src/locales/pl.json`.
- **Следующий шаг (по-прежнему только по решению владельца):** при желании связать риск с рекомендуемой дополнительной работой и позицией сметы — это отдельный вопрос (Stage 11 хранит рекомендации работ), в 15E.2 не делается.

### 15F — выдача документа: журнал, отправка в чат, интерфейс — **реализовано локально 2026-10-08 (15F.1–15F.3); выкладка — 15H**
Решения владельца: PDF отправляется в **чат бота** владельцу; **журнал без файлов**; номер — `KOSZ/2026/10/08/1953` (дата и время выпуска, Europe/Warsaw, при совпадении минуты суффикс `-2`) **плюс сквозной порядковый номер документов одного объекта (клиента)**; предпросмотр черновика сметы — только владельцу.
- **15F.1 — журнал и нумерация (миграция `0038`).** Таблица `issued_documents` (владелец, объект, клиент-снимок, вид `ESTIMATE` / `PHOTO_REPORT`, источник и версия, название, `number` (уникален у владельца), `project_seq` (уникален в объекте), версия шаблона, статус `PENDING` / `SENT` / `FAILED`, код ошибки, область (комнаты части отчёта), страницы, размер, SHA-256, моменты). Номер и порядковый номер присваиваются **при запросе** под блокировкой строки объекта (без гонок, проверено на PostgreSQL); неудачная попытка остаётся в журнале как `FAILED` (номера не «пропадают» молча); повторное нажатие, пока идёт та же выдача, возвращает ту же запись (нет дублей); зависшая `PENDING` старше 15 минут считается `FAILED` (перезапуск сервера).
- **15F.2 — выпуск и отправка.** `POST /projects/{p}/documents` проверяет всё дешёвое сразу (владелец, статус сметы `FINAL` / `ACCEPTED`, профиль исполнителя, лимит 60 фото) и отвечает `202` с записью журнала; формирование PDF и отправка идут **фоновой задачей** (один рендер за раз, не более 3 в очереди → `DOCUMENT_QUEUE_FULL`); отправка — прямым вызовом Bot API `sendDocument` с токеном бэкенда в чат владельца (`chat_id` = его Telegram id), токен никогда не попадает в журнал, логи и сообщения об ошибках; ошибки: чат недоступен (нажмите Start у бота), Telegram недоступен, рендер занят / превысил время / слишком большой. Дополнительно: `GET` журнала и записи (для опроса), `GET /projects/{p}/photo-report/summary` (число фото, по комнатам, лимит — для выбора части отчёта), `POST /projects/{p}/estimates/{e}/preview-pdf` (черновик сметы с водяным знаком в чат, без номера и без записи в журнал).
- **15F.3 — интерфейс.** «Wyślij PDF» у сметы (для черновика — «Podgląd PDF»), у объекта — «Raport fotograficzny» со сводкой и выбором комнат, если фото больше лимита, и журнал «Wysłane dokumenty» (номер, вид, дата, статус); мобильные правила (320–412 px, цели ≥ 44 px), PL / RU, понятные сообщения по кодам ошибок.
- **Итог реализации и отличия от наброска:** (1) номер и порядковый номер присваиваются под блокировкой строки **владельца** (а не объекта): номер уникален у владельца, и PostgreSQL-тест показал, что блокировки объекта мало; (2) в шапке документа печатается «Nr kolejny dokumentu dla obiektu»; (3) очередь — не более 3 документов одновременно (`DOCUMENT_MAX_ACTIVE`), одинаковый запрос во время работы возвращает ту же запись; (4) отправка — прямым вызовом Bot API с токеном бэкенда (отдельный процесс бота не нужен), токен не попадает в логи (логгеры `httpx` / `httpcore` подняты до WARNING) и в тексты ошибок; (5) экраны: кнопка в сводке сметы («Wyślij PDF» / «Podgląd PDF (wersja robocza)») и карточка «Dokumenty PDF» в объекте (закрыта по умолчанию, ничего не грузит до открытия) со сводкой отчёта, выбором комнат при превышении лимита и журналом; (6) тексты для экрана выбираются по стабильным кодам, тест сверяет коды бэкенда с PL / RU словарями.
- **Вне 15F:** файлы в журнале не хранятся — повторная выдача формирует новый документ с новым номером; выкладка и замер времени на сервере — 15H.

#### 15E.3 — «риск → работа → цена» в рапорте осмотра (**реализовано локально 2026-10-08**, старт и решения владельца)
Решения владельца: (1) **цена берётся из текущей сметы**; (2) **в выпущенном документе не должно быть неизвестных цен**; (3) оформлять **отдельным блоком** «Рекомендуемые доп. работы».
- **Блок «Rekomendowane prace dodatkowe»** — после всех фото рапорта, на отдельной странице (короткий блок не рвётся; длинный переносится с повторяющейся шапкой и итогом): работа (польское название), место «Pomieszczenie › Powierzchnia», **причина** (название риска / находки), единица, количество, цена за единицу, стоимость и «Razem — rekomendowane prace dodatkowe». Цифры печатаются **как в позиции сметы** (ничего не пересчитывается). Примечание «Ceny wg kosztorysu, wersja N» (для черновика — «(wersja robocza)»).
- **Какие работы попадают:** активные рекомендации Stage 11 в статусе PENDING и ACCEPTED (отклонённые — нет) для живого, не архивного осмотра живой комнаты, нацеленные на стену, потолок или пол; рекомендация «на всё помещение» не имеет поверхности для цены и в документ не идёт. Одна работа на одной поверхности — одна строка, со всеми причинами.
- **Откуда цена:** «текущая смета» = последняя не архивная смета объекта (по версии); цена — позиция **той же работы на той же поверхности** (не строка проёма). Для принятой рекомендации берётся позиция прайс-листа, с которой её приняли, иначе — по коду работы владельца.
- **Нет цены → документ не выпускается** (`RECOMMENDED_WORK_UNPRICED`, 422, до чтения фото): работа без позиции в смете, позиция «do ustalenia», объекта без сметы. В ответе — список «Комната › Поверхность: работа». Выход для владельца: принять рекомендацию в осмотре (она попадёт в план работ и смету) или отклонить её. Сводка (`photo-report/summary`) сообщает `recommended_count` и `unpriced_works`, карточка «Dokumenty PDF» показывает список и не даёт нажать «Wyślij PDF», пока цены не определены.
- **Часть отчёта по комнатам** проверяет и печатает только работы своих комнат.
- Выкладка — вместе с 15H (миграций нет).

### 15G — каркас договоров и протоколов (без юридических текстов) — **реализовано локально 2026-10-08**
- **Реестр видов** (`documents/registry.py`): к смете и фотоотчёту добавлены `CONTRACT` (договор), `HANDOVER_PROTOCOL` (протокол передачи), `CONCEALED_WORKS_PROTOCOL` (протокол скрытых работ), `FINAL_PROTOCOL` (итоговый протокол). Для каждого вида в реестре: файл шаблона, версия (`skeleton-1`), **префикс номера** (`KOSZ`, `FOTO`, `UMOWA`, `PRZEK`, `ZANIK`, `ODBIOR`; журнал 15F берёт префиксы из реестра — один источник) и **ключи секций** — внутренние идентификаторы без слов (`subject`, `scope_of_work`, `price`, … — предложение структуры для Stage 16; названия и тексты секций пишет Stage 16 / 17).
- **Один общий шаблон** `skeleton.html.j2` на все четыре вида: шапка (название документа, номер, «Nr kolejny dokumentu dla obiektu», дата, место), блоки «Wykonawca» / «Zamawiający», «Obiekt», пронумерованные секции, «Załączniki», блок подписей, колонтитул «Strona X z Y». Секция **без названия и без текста**: печатает «Sekcja n» и «— do uzupełnienia —», пока вызывающий код (Stage 16) не передаст `SectionContent(title, paragraphs)` как данные; неизвестный ключ секции — ошибка `SKELETON_SECTION_UNKNOWN`. Названия документов — только имена («Umowa», «Protokół przekazania», …).
- **Защита от юридического текста:** тест проверяет, что у каркаса всего 8 подписей, каждая короче 40 знаков, не заканчивается точкой и не содержит слов-признаков положений (ссылки на статьи и нормы, «odpowiedzialność», «gwarancja», «kara», «wynagrodzenie», «termin» …), а в самом шаблоне нет собственных слов — всё приходит из подписей или данных.
- **Не входит:** выпуск этих документов (журнал 15F принимает пока только смету и фотоотчёт; для договоров и протоколов Stage 16 добавит миграцию и вид журнала), HTTP-маршруты и экраны.

### 15H — итоговая проверка и выкладка
- Состязательная проверка (как 14J): ограничения ресурсов на 1 OCPU, большие документы, русские / польские символы, матрица владельцев; сборка образа backend с новыми системными библиотеками, миграции `0037…` (+ журнал), пересборка образов бэкапа, выкладка с «да» на каждый шаг, проверка владельцем на телефоне (получить PDF сметы и фотоотчёта в чате и открыть).

## 4a. Результат 15B: как устроен движок (для следующих подэтапов)

Код: `backend/app/domain/documents/`. Как добавить документ (15D, 15E, 15G): 1) вид в `registry.DocumentKind` и запись `DocumentTemplate(kind, version, file)`; 2) шаблон `templates/<имя>.html.j2`, наследующий `_layout.html.j2` (блок `body`); 3) польские подписи — только в `locales/pl.json` (шаблон берёт их через `t('ключ')`; неизвестный ключ — ошибка, лишний ключ — ошибка теста); 4) данные — готовая модель (`DocumentLayout` с `DocumentMeta`, `Party`, плюс собственные поля шаблона), суммы и количества приходят из снимков, шаблон их только форматирует фильтрами `money`, `qty`, `area`, `percent`, `date`, `datetime`; 5) `render_html(template, context)` → HTML, `DocumentRenderer.render(html, assets)` → `RenderedPdf(pdf, pages, sha256, byte_size, render_seconds, worker_pid)`.

Гарантии движка (проверены тестами и мутациями):
| Тема | Как |
|---|---|
| Процесс | PDF делает отдельный процесс (`render_worker`), в своей группе процессов; один рендер за раз, второй ждёт `DOCUMENT_RENDER_WAIT_SECONDS`, потом `DocumentRenderBusyError` |
| Время и память | Таймаут `DOCUMENT_RENDER_TIMEOUT_SECONDS` (процесс убивается вместе с группой), лимиты адресного пространства (`DOCUMENT_RENDER_MEMORY_MB`), времени процессора и размера файла внутри процесса; отмена вызова тоже убивает процесс |
| Размеры | `DOCUMENT_MAX_HTML_BYTES`, `DOCUMENT_MAX_ASSETS`, `DOCUMENT_MAX_ASSET_BYTES`, `DOCUMENT_MAX_PAGES`, `DOCUMENT_MAX_PDF_BYTES` (меньше 50 МБ лимита Telegram), всё → `DocumentTooLargeError` |
| Ресурсы | Читаются только `data:`-адреса, встроенные шрифты и файлы самого документа (`assets/…`); `http`, `ftp`, чужие файлы и выход через `..` отклоняются двумя независимыми проверками; процесс получает минимальное окружение без секретов |
| Данные | Автоэкранирование (имя клиента с разметкой не ломает страницу), недостающее значение — ошибка, а не пустая строка; данные не попадают в таблицу стилей (колонтитул — «бегущий элемент» HTML) |
| Шрифт | DejaVu Sans (Regular, Bold) лежит в репозитории с лицензией, встраивается в PDF: польские буквы, кириллица (имена клиентов) и символы одинаковы на любом сервере; системные библиотеки и шрифт-запас ставит `backend/Dockerfile` |
| Форматирование | `1 234,50 zł`, `12,50 m²`, даты `дд.мм.гггг` по польскому времени; только `Decimal` / `int` / `str`, `float` отвергается; округление «half-up» |
| Остаток | Временная папка `pe-doc-*` удаляется при успехе, ошибке, таймауте и отмене |

Контрольная страница: вид `DIAGNOSTIC` (польские и русские буквы, символы, таблица с повторяющейся шапкой, номера страниц, подписи): ею проверяются шрифты и оформление на сервере.

## 5. Риски
| Риск | Мера |
|---|---|
| Образ backend вырастет, на ARM64 сборка и системные библиотеки могут отличаться от среды разработки | Сборка и проверка в 15H (A4 с откатным тегом); версии пакетов зафиксированы |
| Рендер большого отчёта перегружает 1 OCPU / 6 ГБ | Отдельный процесс, таймаут, лимит памяти, один одновременно, лимит фото и размера картинок |
| Названия позиций сметы хранятся как ключи перевода | Польский словарь на backend + тест покрытия; ключи без перевода — ошибка теста, а не пустая строка в PDF |
| Telegram `sendDocument` недоступен (бот заблокирован / не запущен) | Структурированная ошибка в интерфейсе; файл не теряется (создаётся заново) |
| Неверные суммы в документе | Суммы только из снимка сметы, никаких пересчётов в шаблоне; тест на равенство |

## 6. Открытые вопросы владельцу (задаются в момент нужного подэтапа)
