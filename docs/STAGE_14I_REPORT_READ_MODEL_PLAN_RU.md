# Stage 14I — read model фото для отчёта (Stage 15): план

Статус: **план 2026-10-08, старт одобрен владельцем («давай делать 14I»)**. Архитектура утверждена ранее: `docs/STAGE_14_PHOTO_FIXATION_ARCHITECTURE.md` §5 (`include_in_report`), §14 (read-контракт Stage 15), §19 (строка 14I), решения D14-20 / OD-6. Не входят: вёрстка PDF, шаблоны, выбор фото в интерфейсе, HTTP-маршрут, миграция.

## 1. Что уже есть и чего нет

- **Есть:** все данные Stage 14: фото (`photo_assets`), вложения во все контексты с категорией, подписью, `position` и флагом `include_in_report` (по умолчанию `false`, переключается в просмотрщике «в отчёт»), метки с контурами (`photo_annotations`), находки с `lineage_id`, фото выполнения с `occurrence_key`. Список фото для интерфейса (`PhotoQueryService.list_photos`) постраничный и идёт по фильтрам одного контекста.
- **Нет:** единого чтения «все фото проекта, отобранные для отчёта, в порядке документа»: Stage 15 пришлось бы самому обходить контексты, дублировать правила видимости и порядка. 14I даёт это чтение один раз.

## 2. Что делает 14I

Один **сервис только для чтения** `PhotoReportReadModel` (`backend/app/domain/services/photo_report_read_model.py`): по проекту владельца возвращает дерево неизменяемых dataclass-ов (не ORM, не HTTP-схемы), которое Stage 15 кладёт в шаблон. Сервис ничего не пишет, не вызывает хранилище и не выдаёт ссылок.

### Правила (по умолчанию; владелец может изменить)

| № | Правило | Решение |
|---|---|---|
| R1 | Какие фото | только вложения с `include_in_report = true` (параметр `only_included=True`; `False` отдаёт все видимые фото, нужен для проверок и предпросмотра) |
| R2 | Видимость | как везде: READY-актив, неархивные вложение и актив, вся цепочка владельца (`attachment.project_id = asset.project_id = project`, `asset.owner_id = owner`); чужое и выдуманное → проект не найден |
| R3 | Архивные цели | фото архивной комнаты, поверхности, проёма или осмотра в отчёт **не попадают** (владелец убрал объект с экрана — в клиентском документе его быть не должно); сами фото и данные не меняются |
| R4 | Структура | `project` → фото объекта; `rooms[]` → фото комнаты, `surfaces[]` → фото поверхности, `openings[]` → фото проёма; у комнаты `inspections[]` (цель: поверхность / плоскость пол или потолок / вся комната) → фото осмотра, `questions[]` → фото вопроса, `findings[]` (по `lineage_id`) → фото находки; у поверхности `works[]` по `occurrence_key` (текущие и отвязанные) → фото выполнения |
| R5 | Находка | одна запись на `lineage_id`; заголовок берётся у активной строки, иначе у последней (по `position`, `created_at`, `id`); фото собираются со всех строк линии |
| R6 | Работа | `occurrence_key`, `price_item_id`, код и ключ названия позиции прайса, признак `current` (есть ли ещё в плане поверхности); категории порядка выполнения: BEFORE → PREPARATION → IN_PROGRESS → HIDDEN_WORK → AFTER, остальные после |
| R7 | Порядок | иерархия документа (объект → комнаты → поверхности → проёмы / осмотры / находки / работы), затем `position`, `captured_at` (пустые в конце), `uploaded_at`, `id`; комнаты и проёмы — по `created_at`, `id`; поверхности — по `position` (пустые в конце), `created_at`, `id`; результат полностью детерминирован |
| R8 | Пустые узлы | узел без отобранных фото и без отобранных потомков в результат не входит (отчёт не пустеет «заголовками») |
| R9 | Поля фото | вложение: `attachment_id`, `asset_id`, `context`, цели, `category`, `caption`, `include_in_report`, `position`; актив: `width`, `height` (после ориентации), `content_type`, `byte_size`, `sha256`, `captured_at`, `uploaded_at`, **ключи хранилища `display` и `original`** (оригинал — только для сервера, для PDF высокого качества), миниатюры нет; метки: `x`, `y`, `label`, `position` и `outline` (точки контура или `None`) |
| R10 | Ссылки | никаких presigned-ссылок: Stage 15 читает байты через порт хранилища по ключам; ключи не уходят в HTTP-ответы (HTTP-маршрута нет) |
| R11 | Запросы | число SQL-запросов **не зависит от числа фото** (по запросу на слой: фото + активы, метки, комнаты, поверхности, проёмы, осмотры, находки, вопросы, работы / позиции прайса) |

### Границы
- Нет HTTP-маршрута, нет схемы ответа в OpenAPI, нет интерфейса, нет миграции: **выкладывать нечего**, код поедет с ближайшей выкладкой backend. Данные в production не меняются.
- Названия остаются **ключами / исходными именами** (`name`, `label_key`, `text_key`, `name_key`): перевод и клиентский язык (PL) — задача Stage 15.
- Выбор фото в отчёт остаётся флагом `include_in_report` на вложении (одно и то же изображение в разных местах может быть выбрано по-разному).
