# Stage 19 — Офлайн-черновики: аудит, вопросы и план реализации

Статус: **план v2 (2026-10-15): решения владельца приняты** — Q1 = вариант A (офлайн в уже открытом приложении), Q3 = лимит очереди фото 200 МБ (предупреждение на 160 МБ), Q5 = вариант (б) (у ожидающей записи — её размеры с меткой «~»), Q8 принято, остальные вопросы — по рекомендации (Q2 — править и создавать, Q4 — «последняя запись побеждает» + список «требует внимания»). Подэтап **19B начат** по слову владельца.

## 1. Что такое Stage 19

Дорожная карта: **«Offline drafts — IndexedDB draft storage and sync for no-signal sites (basements, reinforced-concrete buildings), without compromising backend consistency.»** Правило проекта (frontend, Rule E): замеры комнат, фото осмотров и заметки на месте должны вноситься без устойчивой связи, синхронизация не должна ломать согласованность базы. Отложенный пункт 14E.8 (очередь фото без связи) — в бэклоге с Stage 14, владелец решал «отдельно или внутри Stage 19».

**Входит:** показ уже открытых объектов без связи; запись изменений на телефоне и отправка при появлении связи; фото без связи; понятный индикатор «офлайн / ждёт отправки / отправлено / требует внимания».
**Не входит:** работа нескольких устройств одновременно (в MVP владелец один); офлайн-расчёты смет, выдача PDF, договор и протоколы (нужен сервер); шифрование хранилища на телефоне (см. Q8).

## 2. Аудит: что уже есть

| Что | Состояние |
|---|---|
| **Хранилище на телефоне** | Только `localStorage`: токен `access_token`, язык, режим комнаты, размеры проёмов «по умолчанию». **IndexedDB не используется.** Зависимостей `idb` / Dexie нет. |
| **Service worker / PWA** | **Нет.** Приложение — SPA на Vite, загружается по адресу из Telegram; без связи при холодном старте страница не откроется. |
| **Слой запросов** | Один `apiRequest` (токен из `localStorage`, `ApiError`); все `api/*.ts` ходят через него. Кэша чтения и очереди записи нет. |
| **Очередь фото** | `PhotoUploadQueue` (Stage 14): одна полоса, **стабильный `upload_id` (идемпотентность)**, повтор «сначала GET», **но в памяти** (решение D2 «ничего не сохраняется»): закрытие приложения теряет очередь. |
| **Идентификаторы** | Все сущности — UUIDv4, но **выдаёт сервер**; создающие запросы `POST` не принимают `id` (кроме фото `upload_id`). Архитектурные правила прямо предусматривают «генерацию UUID офлайн». |
| **Записи на месте (число изменяющих маршрутов)** | комнаты 4, стены 5, проёмы 4, прямоугольники пола/потолка 4, осмотры 7 (ответы — `PUT` полным набором, идемпотентно), заметки 3, фото 10, статусы выполнения работ (в `work_plans`/execution), + документы 11, смета 7, договор 6 (серверные, офлайн не нужны). |
| **Конкурентность** | Версий/ETag нет; есть `updated_at`. Владелец один, обычно одно устройство. |
| **Расчёты** | Площади, нетто, вычеты — **на сервере** (правило «бизнес-расчёты не во frontend»). Офлайн-экран не может показать пересчитанное. |
| **Сессия** | JWT на 7 дней в `localStorage`; при истёкшем токене приложение входит заново по `initData` Telegram (без пароля). |
| **Среда** | Telegram Mini App: WebView телефона. IndexedDB в нём работает; **service worker в Telegram для iPhone (WKWebView) — под вопросом, проверить на устройстве**. Свободное место и вытеснение хранилища ОС не контролируем. |

**Главный вывод аудита.** Самый частый сценарий владельца — приложение **уже открыто** (связь была на улице), он спускается в подвал, связь пропадает, и нужно продолжить замеры/осмотр/фото. Для него service worker не нужен: достаточно (1) помнить уже загруженные данные, (2) складывать правки в очередь на телефоне, (3) отправлять их, когда связь вернётся. «Холодный старт без связи» — отдельная, более рискованная задача (см. Q1).

## 3. Предлагаемая архитектура

1. **Слой хранения** (`offline/store`): IndexedDB (библиотека `idb`, ~1 КБ, без своих зависимостей), хранилища: `readCache` (ответы GET по ключу «путь + владелец»), `outbox` (очередь операций), `blobs` (фото), `meta` (владелец, время). Данные принадлежат владельцу: при смене пользователя — очистка.
2. **Кэш чтения** (stale-while-revalidate в `apiRequest` для GET из списка разрешённых маршрутов): при ошибке сети показывается последняя сохранённая копия с пометкой «данные от HH:MM». Кнопка «Przygotuj do pracy offline» на карточке объекта заранее загружает всё, что нужно на месте (комнаты, стены, проёмы, прямоугольники, осмотры + справочники осмотра).
3. **Очередь записи** (`outbox`): каждая операция = `{ id операции, метод, путь, тело, зависимости, время, статус }`; отправка **одной полосой по порядку**, при появлении связи (`online`, возврат в приложение, таймер 30 с пока есть очередь) и по кнопке «Synchronizuj». Повтор с задержкой; 4xx сервера не повторяются, а попадают в список «Wymaga uwagi».
4. **Идентификаторы с клиента.** Создающие маршруты (комната, стена, проём, прямоугольник, заметка) получают **необязательное** поле `id` (UUIDv4): повтор того же `id` с тем же телом возвращает уже созданную запись (идемпотентно), с другим телом — `409`. Так дочерние записи ссылаются на родителя ещё до его отправки, переназначения идентификаторов не нужно. Миграция **не нужна** (первичные ключи уже UUID).
5. **Фото:** `PhotoUploadQueue` получает постоянное хранилище (файл в `blobs`, тот же `upload_id`), очередь переживает закрытие приложения (закрывает 14E.8).
6. **Согласованность:** операции выполняются в порядке создания; удаление/архив родителя до отправки детей обрабатывается явно (дети получают ошибку «родитель не найден» → «требует внимания», данные не теряются). Правка записи, которую сервер уже изменил (другое устройство): по умолчанию «последняя запись побеждает», при отказе сервера — в список «требует внимания».
7. **Интерфейс:** индикатор в шапке (● онлайн / ⚠ офлайн / ⟳ N ждут); пометка «ждёт отправки» на записи; экран «Синхронизация» (что в очереди, что отправлено, что отклонено, кнопки повторить/отменить/отправить); на мобильном — по правилам проекта (вертикально, ≥ 40 px, PL/RU).
8. **Что остаётся только онлайн** (честное сообщение «нужна связь»): смета и её расчёт, выдача PDF, договор и протоколы, прайс, календарь и напоминания, настройки.

## 4. Риски и ограничения

- **Расчёты на сервере:** без связи площадь новой стены не пересчитывается. Варианты — Q5.
- **Холодный старт без связи** зависит от service worker и поведения Telegram на iPhone — проверка на реальных устройствах до решения.
- **Место и вытеснение:** фото до 25 МБ; нужен лимит очереди и предупреждение; ОС может очистить хранилище неактивного приложения — поэтому очередь показывается, и после синхронизации записи удаляются.
- **Приватность:** на телефоне лежат имена клиентов, адреса и фото (Q8).
- **Побочные эффекты на сервере:** создание работ меняет календарь/напоминания (Stage 18): они пересчитываются при отправке, не при записи на телефон.
- **Тестирование:** реальную потерю связи в Telegram автотестами не проверить; нужны сценарий «режим полёта» на телефоне и режим offline в Chromium (Playwright).

## 6. Выкладка

Frontend + небольшое изменение бэкенда (необязательное `id`): обычная выкладка без миграции; добавление зависимости `idb` меняет `package.json`, поэтому полная выкладка скриптом, а не только-frontend. Бэкап базы перед ней не обязателен (схема не меняется), но рекомендую свежий.

## 7. Решения владельца (вопросы с рекомендациями; принято: Q1 = A, Q3 = 200 МБ, остальное по рекомендации)

1. **Q1. Какой офлайн нужен?** (A) приложение уже открыто, связь пропала — продолжаем работу; (B) ещё и открыть приложение без связи (service worker). **Рекомендация:** A сначала; B решаем в 19F по результату проверки на ваших телефонах (на iPhone в Telegram может не работать).
2. **Q2. Что можно делать без связи?** (1) править существующее: размеры, ответы осмотра, статусы работ, заметки; (2) ещё и **создавать** новые комнаты/стены/проёмы/прямоугольники. **Рекомендация:** оба уровня (замеры на месте — главный сценарий), с клиентскими `id`.
3. **Q3. Фото без связи** — в очередь на телефоне (внутри Stage 19, закрывает 14E.8). Лимит очереди? **Рекомендация:** да; лимит 200 МБ и предупреждение на 80 %.
4. **Q4. Конфликты:** владелец один — «последняя запись побеждает», а то, что сервер отклонил, показывается в «требует внимания», ничего не пропадает молча. **Рекомендация:** так.
5. **Q5. Площади и итоги без связи:** (а) только «ждёт отправки» без чисел; (б) простой предварительный показ «ширина × высота» у ожидающей записи с меткой «~, после синхронизации». **Рекомендация:** (б) только для самой записи; итоги комнаты/объекта и сметы остаются серверными.
6. **Q6. Только онлайн:** смета, PDF, договор, протоколы, прайс, календарь, настройки. **Рекомендация:** согласиться.
7. **Q7. Отправка:** автоматически при возвращении связи + кнопка «Synchronizuj»; порядок по времени записи. **Рекомендация:** так.
8. **Q8. Данные на телефоне:** хранить без отдельного шифрования (защита — блокировка телефона и песочница Telegram), токен в IndexedDB не кладём, при смене пользователя и по кнопке «Очистить офлайн-данные» всё удаляется. **Рекомендация:** так (шифрование — позже, если потребуется).
9. **Q9. Токен:** при истёкшем токене после возврата связи приложение само входит по `initData` и продолжает отправку. **Рекомендация:** так.
10. **Q10. Срок и размер кэша чтения:** 30 дней без обращения, очистка старых объектов. **Рекомендация:** так.
11. **Q11. Подготовка:** кнопка «Przygotuj do pracy offline» на объекте + автокэш всего, что вы открывали. **Рекомендация:** оба.
12. **Q12. Бэкенд:** необязательное `id` в создающих запросах (идемпотентно), без миграции. **Рекомендация:** так.

14. **Q14. Проверка:** режим offline в Chromium + ваш «режим полёта» на телефоне по сценарию, который я напишу (замер, осмотр, фото, возврат связи). **Рекомендация:** так.

## 8. Примечания к реализации 19B (2026-10-15)

- **Хранилище:** IndexedDB через библиотеку `idb` (зависимость времени выполнения) и `fake-indexeddb` (только для тестов). База `plan-estimate-offline`, хранилище `readCache` — ключ `владелец|путь`, значение `{ данные, время сохранения }`. Идентификатор владельца берётся из входа (`offline_owner` в `localStorage`); при смене владельца кэш очищается.
- **Кэш чтения** встроен в `apiRequest`: GET из разрешённого списка (проекты, комнаты и всё под ними, заметки, клиенты) после успеха сохраняется; при **сетевой ошибке** (не при ответе сервера 4xx/5xx) отдаётся последняя копия и включается признак «данные из памяти телефона от HH:MM». Фото, документы, смета, договор, календарь, прайс и аутентификация в кэш не попадают.
- **Состояние связи:** не по `navigator.onLine` (в подвале он часто врёт), а по результатам запросов; плюс события `online/offline` и проверка `/api/health` каждые 15 с, пока связи нет.
- **Индикатор:** строка под шапкой «Brak połączenia — dane zapisane na telefonie (z HH:MM)» только когда связи нет или показана копия.
- **«Przygotuj do pracy offline»** на объекте: последовательно загружает объект, его комнаты, поверхности, проёмы, прямоугольники, осмотры и ответы, заметки; показывает ход «12 / 40»; без связи не запускается.
- **«Wyczyść dane offline»** в окне аккаунта.

## 9. Примечания к реализации 19D (2026-10-16)

- **Фото без связи (закрывает 14E.8).** Неотправленные фото лежат в IndexedDB (версия 3): `photos` — сведения о фото (владелец, цель, `upload_id`, имя, тип, размер, состояние, число попыток, причина отказа), `photoFiles` — байты как `ArrayBuffer`. Запись — при постановке в очередь; удаляется после отправки, отмены или закрытия строки. После перезапуска приложения очередь восстанавливается при входе (`restorePhotoQueue` в `useAuth`); байты остаются на диске, пока очередь не дойдёт до фото (память телефона не забивается).
- **Очередь ждёт**, пока нет связи или пока не ушли более старые правки из очереди изменений (фото может относиться к комнате или стене, сделанным без связи); отклонённая правка очередь не держит. Связь пропала посреди отправки — фото возвращается в ожидание, ничего не засчитывается в попытки; затем сначала `GET` по `upload_id`: есть на сервере → готово, нет → отправка с тем же `upload_id` (идемпотентность Stage 14).
- **Лимит Q3:** 200 МБ ожидающих фото, предупреждение с 160 МБ; лишние файлы выбора отклоняются с сообщением. Истёкший токен: тихий повторный вход по `initData` и одна повторная отправка.
- **Что осталось на 19E:** общий экран «что ждёт отправки» (фото + правки + отклонённые), миниатюры восстановленных после перезапуска фото (пока серая плашка с именем), пометки «~ po synchronizacji».
- **Проверка на телефоне (для владельца, после деплоя):** режим полёта → снять 2–3 фото на стене → закрыть приложение → открыть заново (со связью) → фото уходят сами и появляются в списке.
