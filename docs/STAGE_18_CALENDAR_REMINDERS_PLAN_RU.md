# Stage 18 — Календарь и напоминания в Telegram: аудит и план

Статус: **план 18A, версия 1 (2026-10-11), ждёт решений владельца (раздел 6).** Старт этапа одобрен владельцем («переходим к этапу 18 в новой ветке»). Ветка `stage-18` отведена от `stage-17` (Stage 17 ещё не слит в `main`: этап 18 должен содержать всю его работу). Код на этом шаге не пишется.

## 1. Что такое Stage 18

Дорожная карта: **«Calendar and Telegram reminders — Schedule management, milestone reminders and technological-break notifications.»** (зависит от Stage 13: технологические перерывы и учёт выполнения; календарь и напоминания были явно вынесены из Stage 13, решение D12).

**Входит:**
- **Календарь исполнителя** — одна лента «что и когда» по всем объектам: окончание технологических перерывов, начало и конец работ, сроки из договора и протоколов, работы других подрядчиков, свои заметки.
- **Напоминания в Telegram** — личные сообщения владельцу от бота (не клиентам): «можно продолжать», «завтра начало работ», «сегодня истекает срок…».
- **Управление графиком** — минимально: плановая дата у работы (или у помещения) и проверка, что она не раньше конца технологического перерыва. Без автоматического планировщика.

**Не входит:** отправка сообщений клиентам и подрядчикам; email, SMS, WhatsApp; синхронизация с Google Calendar / Outlook (выгрузка `.ics` — возможное расширение, вопрос Q13); повторяющиеся события; планирование ресурсов и бригад; диаграмма Ганта; ИИ (правила проекта: только детерминированно).

## 2. Аудит: что уже есть

| Что | Состояние |
|---|---|
| **Технологические перерывы (Stage 13)** | У каждой работы плана `wait_after_hours` (целые часы или нет); у выполнения `completed_at`. Сервис считает `ready_after = completed_at + wait_after_hours` **при чтении, не хранит**; явно помечено «не напоминание, не событие календаря (Stage 18)» (D-H12). Это главный источник событий |
| **Даты договора (Stage 16)** | В ответах анкеты: `work_start_date`, `work_end_date`, `price_validity_days`, `payment_due_days`, срок явки на приёмку, лимит простоя (`downtime_days_limit`); `signed_on` у подписанного договора |
| **Даты протоколов (Stage 16)** | Передача помещений: `held_on`; скрытые работы: `notified_on`, `held_on`; приёмка: `notified_on`, `renotified_on` (второй вызов, § 14 ust. 5), `held_on`; простой: `noticed_on`, `need_by`, `held_on`; смежные работы: `period_from`, `period_to` |
| **Сроки, вытекающие из договора** | Аванс — 3 дня после заключения (§ 6); явка клиента на приёмку и повторный вызов ≥ 3 рабочих дней (§ 14); замечания клиента — 14 дней после одностороннего протокола; ответ на рекламацию — 14 дней (§ 16); извещение о скрытых работах ≥ 1 рабочий день до закрытия (§ 13); уведомление о простое до конца следующего рабочего дня (§ 10); отказ потребителя — 14 / 30 дней с заключения (§ 20). Нигде не вычисляются как даты |
| **Рабочие дни** | Договор определяет рабочие дни: понедельник–пятница без дней, свободных от работы по закону. **Календаря польских праздников в коде нет** (в `protocols/downtime.py` прямо сказано: «calendar of public holidays is not kept here») |
| **Отправка в Telegram** | Бэкенд уже пишет владельцу в личный чат через Bot API (`TelegramBotApiDelivery`, Stage 15F): токен бота на сервере, `chat_id` = `telegram_user_id`; **только `sendDocument`**, `sendMessage` нет. Токен не должен попасть в лог (защита уже есть) |
| **Фоновые задачи** | **Нет.** Бэкенд — один процесс `uvicorn`, без планировщика и очередей; контейнеров четыре (backend, frontend, caddy, postgres); отдельного процесса бота нет; **Redis запрещён правилами MVP**. Для напоминаний нужен источник времени — это главное архитектурное решение этапа |
| **Бот принимает сообщения?** | Нет: бот только отправляет. Кнопки сообщений с обратным вызовом («Отложить», «Готово») потребовали бы приём обновлений от Telegram (webhook: новый маршрут, секрет, настройка `setWebhook`) — новая поверхность атаки и отдельная выкладка (вопрос Q11) |
| **Язык и часовой пояс** | У пользователя есть `language_code`; в приложении выбор PL / RU; даты в БД — UTC, показ — Europe/Warsaw (как в документах) |
| **Интерфейс** | Шесть пунктов меню; экрана календаря нет; принципы: телефон 320–412 px, без горизонтальной прокрутки, кнопки ≥ 44 px |

Вывод: данные для событий **уже почти все есть**, но нет (1) вычисления дат и рабочих дней, (2) источника времени для отправки, (3) отправки текста, (4) экрана. Недостаёт также **плановых дат работ** (график), если владелец хочет планировать по дням (Q12).

## 3. Принципы

1. **Детерминированно.** Событие и срок вычисляются чистой функцией из данных; одни и те же данные дают одни и те же напоминания. Никакого ИИ.
2. **Не дублировать данные.** События календаря — производные: считаются из исходных таблиц (перерывы, договор, протоколы). Хранится только то, чего нет в источниках: **свои заметки**, **настройки**, **очередь напоминаний** (она — расписание отправки и журнал, а не копия данных).
3. **Идемпотентность.** У каждого напоминания ключ дедупликации (`вид + источник + момент`); повторная сверка не создаёт дублей; изменение исходных данных отменяет или переносит напоминание.
4. **Доставка «не менее одного раза, не больше одного»** на практике: блокировка строки (`FOR UPDATE SKIP LOCKED`), статус `SENT` пишется после ответа Telegram; при сбое — повтор с ограничением числа попыток, дальше `FAILED` с видимой причиной.
5. **Только владельцу.** Никаких сообщений клиентам; сообщения без персональных данных клиента в тексте сверх названия объекта.
6. **Без Redis, без брокера.** Очередь — таблица в PostgreSQL.
7. **Мобильный интерфейс.** Лента-повестка, а не сетка месяца (на 390 px сетка нечитаема); крупные строки; быстрые действия.
8. **Тексты — в словарях PL / RU на сервере и в приложении**, не в коде.

## 4. Предлагаемая архитектура

**Модель событий (чистые функции, без БД — подэтап 18B).** Один тип «событие»: `kind`, `due_at` (UTC), `date`, `project_id`, `source_ref`, заголовок как ключ + параметры. Вычисляется из:
- перерывов: `ready_after` выполненных работ → «можно продолжать: работа / поверхность»;
- договора: начало и конец работ, окончание отказа потребителя, аванс, срок оплаты после счёта, окончание действия цен;
- протоколов: сроки явки и повторного вызова, замечаний, предел простоя, `need_by`;
- смежных работ: начало и конец чужих работ на объекте;
- плановых дат работ (если принято Q12): день работы, конфликт с перерывом.

**Рабочие дни (18B):** функция «добавить N рабочих дней» по правилам договора: пн–пт без государственных праздников Польши. Праздники вычисляются детерминированно (фиксированные даты + подвижные от Пасхи: Пасхальный понедельник, Boże Ciało, Zielone Świątki), включая 24 декабря (с 2025 г. — выходной; подтвердить по закону) — без внешних сервисов.

**Данные (миграция `0054`, подэтап 18C):** три небольшие таблицы, у каждой `owner_id`, UUID, UTC:
- `calendar_notes` — свои заметки: заголовок, дата/время, объект (необязательно), напомнить за (нет / 1 ч / 1 день);
- `reminders` — очередь: `owner_id`, `kind`, ссылка на источник, `due_at`, `send_at`, `status` (`PENDING / SENT / SKIPPED / FAILED / CANCELLED`), `dedupe_key` (уникальный), `attempts`, `sent_at`, `error_code`, параметры текста; удаляется через 90 дней (Q14);
- `calendar_settings` — на пользователя: какие виды событий включены, часы тишины, час утренней сводки, язык сообщений.

**Сверка (18C):** функция «события → напоминания» выполняется по таймеру (раз в 5–10 минут) и при открытии календаря: создаёт недостающие (`INSERT … ON CONFLICT DO NOTHING` по `dedupe_key`), отменяет те, чей источник изменился или исчез, переносит сдвинувшиеся.

**Доставка (18D):** асинхронный цикл внутри бэкенда, запускается в `lifespan` (рядом с проверкой каталога): раз в минуту берёт созданные к отправке напоминания (`SKIP LOCKED`), отправляет `sendMessage` в личный чат владельца, записывает результат. Рекомендация: **внутри бэкенда** (один процесс, меньше выкладочный риск); благодаря `SKIP LOCKED` его позже можно вынести в отдельный контейнер без изменения данных (вопрос Q4). Токен бота — только из окружения, в логах скрыт (механизм Stage 15F).

**Сообщение:** короткий текст на языке владельца + кнопка `web_app` «Открыть» (кнопка-ссылка, **без приёма обновлений**). Часы тишины 21:00–07:00 (Варшава): сообщения откладываются до 07:00; утренняя сводка «что сегодня» (Q3).

**API (18E, только свои данные, `owner_id` во всех запросах):** `GET /api/calendar?from&to&project_id` (события + заметки + напоминания), `POST/PATCH/DELETE /api/calendar/notes`, `GET/PUT /api/calendar/settings`, `POST /api/calendar/reminders/{id}/snooze` и `/done`.

**Экран (18E):** седьмой пункт меню **«Календарь»**: повестка «Просрочено / Сегодня / Завтра / На неделе / Позже», фильтр по объекту, строка = время + что + объект, нажатие открывает нужный экран объекта (перерыв — поверхность, срок договора — договор и т. д.); «Добавить заметку»; «Настройки напоминаний». На экране объекта — плитка «График» (если принято Q12).

## 7. Риски и критерий готовности

| Риск | Что делаем |
|---|---|
| Лишние или дублирующиеся напоминания | Ключ дедупликации + уникальный индекс; тест «повторная сверка ничего не создаёт»; отмена при изменении источника |
| Пропущенные напоминания при перезапуске | Очередь в БД, отправка «с опозданием» по Q9; тест перезапуска |
| Ошибки в рабочих днях и праздниках | Таблица праздников на годы вперёд сверяется с тестом по известным датам; сроки договора проверяются по примерам из самого договора |
| Летнее / зимнее время | Расчёт в Europe/Warsaw, хранение в UTC; тесты на дни перехода |
| Утечка токена бота | Тот же механизм защиты, что в Stage 15F (токен не попадает ни в лог, ни в исключение) |
| Спам владельцу | Часы тишины, утренняя сводка, лимит сообщений в сутки; настройка видов событий |
| Приём обновлений от Telegram | Не делаем в MVP (Q11) |
| Миграция | Отдельная, обратимая; перед выкладкой — свежий бэкап (A9) |

Готово, когда: все подэтапы закоммичены; тесты backend и frontend, `tsc`, `vite build`; напоминание создаётся, отправляется один раз, отменяется при изменении данных (тесты); часы тишины и сводка работают; мобильная проверка 320 / 390 / 412 px PL / RU; владелец получил реальное сообщение от бота и проверил календарь на телефоне.
