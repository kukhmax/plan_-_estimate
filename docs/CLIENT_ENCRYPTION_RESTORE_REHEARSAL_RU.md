# Шифрование данных клиентов — репетиция восстановления из бэкапа с ключом (EN-3c)

Статус: **EN-3c выполнен владельцем на рабочей станции 2026-10-18: PASS — V1 закрыт** (результат — раздел 6; проверенные блоки команд — `docs/CLIENT_ENCRYPTION_RESTORE_REHEARSAL_COMMANDS_RU.md`). Бэклог-пункт, **не этап дорожной карты**. Это последняя часть EN-3 и **условие закрытия V1** (`docs/CLIENT_DATA_ENCRYPTION_PLAN_RU.md`, раздел 4 «Бэкапы»). Предыдущие части: EN-3a (ротация ключа сервера), EN-3b (смена ключа данных) — `docs/CLIENT_ENCRYPTION_KEYS_RUNBOOK_RU.md`.

## 1. Что проверяется и зачем

Бэкап содержит **шифртекст** и **ключи данных, завёрнутые ключом сервера** (`DATA_KEK`). Он стоит ровно столько, сколько стоит **сохранённая копия этого ключа** (менеджер паролей + бумага). Репетиция отвечает на вопрос, который нельзя проверить на живом сервере: **откроется ли настоящий бэкап вашей копией ключа, и только ею?**

Команда `python -m app.cli.restore_key_check` на **восстановленной в scratch-базе** копии бэкапа проверяет (только чтение, печатает числа и 8-значные отпечатки, не ключи и не значения):

1. База называется `pe_restore_scratch…` и стоит на loopback / хосте с `scratch` — иначе отказ **до** любого чтения (код 2). Боевую базу она не откроет.
2. Версия alembic восстановленной базы и версия кода (справочно: «совпадает / отличается»).
3. **Все ключи данных открываются вашим ключом** (`DATA_KEK`; для бэкапа, сделанного **до** ротации ключа сервера — вместе с `DATA_KEK_PREVIOUS` = старый ключ).
4. **Каждое зашифрованное значение расшифровывается**, открытых персональных значений нет (для бэкапов старше EN-2b-1 — `--allow-plain`).
5. **Случайный неверный ключ не открывает ничего** (контроль: шифрование действительно защищает).

Итог: `RESTORE KEY CHECK: PASS` (код 0) или `FAIL (<причины>)` (код 3).

## 2. Что нужно (на рабочей станции W, как в 72.4 боевого runbook)

* Восстановление базы в scratch-PostgreSQL по `docs/PRODUCTION_DEPLOYMENT_RUNBOOK_RU.md` **72.4, шаги 1–3** (restore-пользователь, age-ключ, `restore --phase database`; медиа для этой проверки не нужны).
* **Копия ключа сервера из менеджера паролей** (запись «Plan & Estimate — DATA_KEK») — **не** файл с сервера. Это и есть предмет проверки: сохранённая копия рабочая.
* Для бэкапа до ротации ключа сервера — копия **старого** ключа («выведен из работы, версия N»).
* Образ backend из того же коммита (`git archive` → `docker build -f backend/Dockerfile`), запуск с `--entrypoint python`, чтобы не применялись миграции и не стартовал сервер.

## 3. Порядок (шаблон; **проверенные блоки команд — в `docs/CLIENT_ENCRYPTION_RESTORE_REHEARSAL_COMMANDS_RU.md`**)

1. **Восстановить** нужный бэкап в scratch-базу (72.4, шаги 1–3). Не трогать боевую базу и боевой ключ.
2. **Собрать образ** из коммита ветки: `git archive origin/backlog-client-encryption backend | tar -x -C ~/pe-check && docker build -t pe-backend-check ~/pe-check/backend`.
3. **Проверка вашим ключом** (ключ вводится скрытно, в историю не попадает):

```bash
read -rs -p 'DATA_KEK (копия из менеджера паролей): ' DATA_KEK; echo; export DATA_KEK
docker run --rm --network "$SCRATCH_NET" \
  -e DATABASE_URL='postgresql+asyncpg://<пользователь>@<scratch-хост>:5432/pe_restore_scratch_<имя>' \
  -e PGPASSFILE=/run/pgpass -v "$SCRATCH_PGPASS":/run/pgpass:ro \
  -e DATA_KEK -e DATA_KEK_PREVIOUS \
  --entrypoint python pe-backend-check -m app.cli.restore_key_check
unset DATA_KEK
```

   Ожидается `RESTORE KEY CHECK: PASS`, `data keys: N (open with DATA_KEK alone: N …)`, `values: ciphertext X, plain 0, do not decrypt 0`, `a random wrong key opens a data key: no (expected)`.
4. **Вторая копия ключа — бумага:** повторить шаг 3, **набрав ключ с бумаги** (а не вставив из менеджера). PASS = бумажная копия без опечаток.
5. **Контроль «без ключа не читается»:** повторить шаг 3 с `DATA_KEK=$(openssl rand -base64 32)`. Ожидается `FAIL (DATA_KEYS_DO_NOT_OPEN_WITH_THIS_KEY)`, код 3.
6. **Бэкап до ротации ключа сервера:** если делаете проверку на бэкапе, снятом до ротации EN-3a — PASS только с `DATA_KEK_PREVIOUS` = старый ключ; с одним новым будет FAIL (так и задумано: поэтому старый ключ не удаляют).
7. **Сверка строк** — 72.4, шаг 4 (число строк в восстановленной и боевой базе).
8. **Уборка** — 72.4, шаг 5 (scratch-контейнер и сеть, файлы паролей, API-ключ restore-пользователя).

## 4. Критерий закрытия V1 (PASS репетиции)

* Шаг 3 — PASS (ваша копия из менеджера открывает настоящий бэкап: все ключи данных, все значения, открытых нет);
* Шаг 4 — PASS (бумажная копия работает);
* Шаг 5 — FAIL с кодом `DATA_KEYS_DO_NOT_OPEN_WITH_THIS_KEY` (без ключа бэкап нечитаем);
* версия alembic восстановленной базы = версия кода, число строк сходится.

Результат (строки `RESTORE KEY CHECK`, `data keys`, `values`, без ключей) записывается в `docs/development-progress.md`. После этого V1 закрыт; V2 (EN-4) — только по вашему «да» и подтверждению условий раздела 5 плана.
