# Шифрование данных клиентов — runbook ключей (EN-3)

Статус: **EN-3a (ротация ключа сервера) и EN-3b (смена ключа данных) приняты владельцем (2026-10-18); EN-3c (репетиция восстановления) готов локально.** Бэклог-пункт, **не этап дорожной карты**. **EN-3c** (репетиция восстановления из бэкапа с ключом) готов локально; живую репетицию на ваших бэкапах проводит владелец. План: `docs/CLIENT_DATA_ENCRYPTION_PLAN_RU.md`.

## 1. Какие бывают ключи

| Ключ | Что это | Где живёт | Что защищает |
|---|---|---|---|
| **DATA_KEK** (ключ сервера) | 32 случайных байта, base64 | **только** переменная `DATA_KEK` в `.env.production` на VM + ваши две копии вне сервера (менеджер паролей и бумага) | «заворачивает» ключи данных |
| **Ключ данных (DEK)** | 32 случайных байта, по одному на владельца | в таблице `data_keys`, **только завёрнутым** DATA_KEK; открытым — только в памяти backend | сами значения (`enc1:…`) |

* `DATA_KEK_VERSION` — номер версии ключа сервера (1, 2, …); у каждого ключа данных в базе записано, каким поколением ключа сервера он завёрнут.
* `DATA_KEK_PREVIOUS` — **только во время ротации**: старый ключ сервера. В остальное время пустой.
* Потеря DATA_KEK = потеря данных, записанных шифртекстом. Из базы и бэкапов он не восстанавливается (бэкап содержит только завёрнутые ключи данных и шифртекст).
* V1 защищает от утечки **дампа и бэкапа** и от чтения базы без ключа; **не защищает** от того, кто получил доступ к работающему серверу вместе с `.env.production` (ключ там же). Это сказано заранее и не меняется до V2 (EN-4).

## 2. Ротация ключа сервера (EN-3a)

**Зачем:** подозрение на утечку ключа (файл `.env.production` попал не туда, ушёл доступ к VM), смена людей с доступом, плановая смена раз в год-два. Данные при этом **не перешифровываются и не меняются**: меняется только то, чем завёрнуты ключи данных (по одному на владельца — это мгновенно).

**Как устроено безопасно:** на время ротации backend знает **оба** ключа сервера (новый как `DATA_KEK`, старый как `DATA_KEK_PREVIOUS`) и читает ключи данных при любом из них; новые ключи данных всегда заворачиваются новым. Поэтому на каждом шаге всё читается, а откат возможен до последнего.

**Порядок (скрипт `docs/CLIENT_ENCRYPTION_KEK_ROTATION_RU.sh`, всё по воротам):**
1. Выложена EN-3a (`docs/CLIENT_ENCRYPTION_EN3A_DEPLOY_RU.sh`) — код ротации + пустая строка `DATA_KEK_PREVIOUS` в compose.
2. Свежий бэкап A9 (не старше суток).
3. Создать новый ключ в файле: `docker exec plan_estimate_backend python -m app.cli.rotate_keys new-key > ~/new_data_kek.txt && chmod 600 ~/new_data_kek.txt`; **сохранить его копии** (менеджер паролей «Plan & Estimate — DATA_KEK, версия N+1» и бумага).
4. Запуск: `cd ~/apps/plan_-_estimate && git fetch -q origin backlog-client-encryption && git show origin/backlog-client-encryption:docs/CLIENT_ENCRYPTION_KEK_ROTATION_RU.sh > ~/rotate_kek.sh && bash ~/rotate_kek.sh`
5. Ворота **K** `КЛЮЧ СОХРАНЁН <отпечаток>` — сверка копии нового ключа. Скрипт пишет в `.env.production` новый `DATA_KEK`, версию +1 и старый ключ как `DATA_KEK_PREVIOUS`, пересоздаёт backend и проверяет, что **все данные читаются** (`verify` шифрования) и что все ключи данных открываются старым ключом как «предыдущим».
6. Ворота **R** `ПЕРЕЗАВОРАЧИВАНИЕ ДА` — все ключи данных заворачиваются новым ключом (всё или ничего); данные не затрагиваются.
7. Ворота **P** `СТАРЫЙ КЛЮЧ УБРАТЬ ДА` — `DATA_KEK_PREVIOUS` очищается, backend пересоздаётся; скрипт проверяет, что **всё открывается новым ключом одним** (`rotate_keys verify`, `reencode_data verify`), число строк то же.
8. После «ВСЁ PASS»: бэкап под текущую голову; **удалить с VM** `~/new_data_kek.txt` и `~/.env.production.before-rotation` (`shred -u`); проверить в Mini App.

**Старый ключ не удалять.** Бэкапы, сделанные до ротации, содержат ключи данных, завёрнутые **старым** ключом; открыть их можно только им. Пометьте запись «выведен из работы, версия N» и храните, пока такие бэкапы могут понадобиться (срок хранения бэкапов).

Скрипт можно запускать повторно: середину ротации он узнаёт по `DATA_KEK_PREVIOUS`.

### Команды (внутри backend; печатают только числа)

* `python -m app.cli.rotate_keys status` — сколько ключей данных открывается текущим ключом / только предыдущим / ни одним.
* `python -m app.cli.rotate_keys rewrap` — перезавернуть (всё или ничего).
* `python -m app.cli.rotate_keys verify` — выход 0 только когда **все** открываются текущим ключом одним (тогда `DATA_KEK_PREVIOUS` можно убирать).
* `python -m app.cli.rotate_keys new-key` — напечатать новый ключ (ничего не сохраняет).

## 3. Что если…

* **Ключ сервера потерян, копий нет:** данные в `enc1:` восстановить нельзя. Поэтому две копии вне сервера создаются **до** первой выкладки и сверяются по отпечатку (8 знаков SHA-256).
* **Ключ утёк, ротация нужна срочно:** шаги 2–7 выше; старые бэкапы после этого всё ещё открываются старым ключом, который уже скомпрометирован. Если утекли и бэкапы, ротация ключа сервера защищает только **новые** копии базы; старые копии защищены прежним ключом.
* **Ротация остановилась посреди пути:** ничего не потеряно; backend читает при двух ключах. Повторный запуск скрипта продолжит; откат до ворот R — вернуть `~/.env.production.before-rotation` (команда печатается при отказе).
* **backend не стартует после правки `.env.production`:** в логе будет `DATA_KEK` / `DATA_KEK_PREVIOUS` — значение не base64 из 32 байт; верните файл-копию.

## 4. Выбор пользователя: «шифровать именно этого клиента»

Сейчас **шифруется всё** (все клиенты, объекты, представители, заметки, документы, расчёты) одним ключом данных владельца. В V1 выбор «шифровать / не шифровать» отдельных записей **ничего бы не добавил к защите** (ключ один и тот же, сервер расшифровывает всё одинаково), а только создал бы незащищённые исключения. Содержательный выбор появляется в **V2 (EN-4)**: «особо защищённый» клиент или объект, чьи данные завёрнуты **ключом, которого нет на сервере** (хранится у вас на телефоне). Цена: такие записи нельзя искать, показывать в напоминаниях бота и собирать в документы без открытой сессии Mini App. Это решается на воротах EN-4.

## 5. Смена ключа данных (EN-3b)

**Зачем:** подозрение, что утёк именно **ключ данных** владельца (а не ключ сервера: его меняет раздел 2). Смена ключа сервера ключ данных не меняет: она лишь перезаворачивает его. Чтобы данные перестали зависеть от возможно утёкшего ключа данных, каждое значение нужно зашифровать **новым** ключом данных.

**Порядок (скрипт `docs/CLIENT_ENCRYPTION_DEK_ROTATION_RU.sh`, всё по воротам; перед этим выложена EN-3b — `docs/CLIENT_ENCRYPTION_EN3B_DEPLOY_RU.sh`):**
1. Свежий бэкап A9 (не старше суток).
2. Ворота **S** `НОВЫЙ КЛЮЧ ДАННЫХ ДА` — каждому владельцу создаётся новый активный ключ данных; старый остаётся (неактивный), чтобы читать то, что им зашифровано; backend **пересоздаётся**, чтобы не писать старым ключом из памяти. Данные читаются весь путь.
3. Ворота **R** `ПЕРЕШИФРОВКА ДА` — каждое значение, зашифрованное не активным ключом, расшифровывается старым и шифруется новым (порциями, повторяемо; «дата изменения» записи не меняется; значение, изменённое в это время, не затирается и находится следующим проходом). Скрипт проверяет: под старым ключом 0 значений, `verify` шифрования проходит, число строк то же.
4. Ворота **P** `СТАРЫЙ КЛЮЧ ДАННЫХ УДАЛИТЬ ДА` — неактивные ключи, которыми не зашифровано ни одно значение, удаляются из базы (**команда откажется**, если хоть одно значение ещё под ними), backend пересоздаётся — старый ключ уходит и из памяти. Необратимо для живой базы.
5. После «ВСЁ PASS»: бэкап под текущую голову (в нём значения уже под новым ключом).

**Что остаётся от старого ключа данных:** только в бэкапах, сделанных **до** смены (в виде завёрнутого ключом сервера значения). Они по-прежнему открываются ключом сервера. Если причина смены — утечка ключа данных и вместе с ней мог утечь старый бэкап, смена защищает только **новые** копии базы.

**Команды** (внутри backend; печатают только числа и первые 8 знаков идентификаторов):
* `python -m app.cli.rotate_data_keys status` — по владельцам: какие ключи данных есть, активный ли, сколько значений каждым зашифровано; выход 0 только когда **все** значения под активными ключами.
* `start --owner <uuid> | --all` — новый активный ключ (отказ, пока предыдущая смена не закончена).
* `reseal [--owner <uuid>] [--limit N]` — перешифровка (выход 3, если значение не расшифровалось, изменилось во время работы или остались под старым ключом).
* `retire [--owner <uuid>]` — удалить неактивные ключи без значений (выход 6 и ничего не удалено, если какой-то ключ ещё что-то шифрует).

## 6. Репетиция восстановления из бэкапа с ключом (EN-3c)

Бэкап стоит ровно столько, сколько стоит **сохранённая копия ключа сервера**. Поэтому перед закрытием V1 один раз проверяется на настоящем бэкапе, восстановленном в scratch-базу: открывается ли он копией ключа из менеджера паролей и копией с бумаги, и **не** открывается ли случайным ключом. Команда `python -m app.cli.restore_key_check`; полный порядок и критерии PASS — `docs/CLIENT_ENCRYPTION_RESTORE_REHEARSAL_RU.md`. Бэкап, снятый **до** ротации ключа сервера, открывается только вместе со старым ключом (`DATA_KEK_PREVIOUS`).

## 7. Что проверено (EN-3a)

* `backend/tests/test_en3a_kek_rotation.py` (15): ключ данных открывается текущим, затем предыдущим ключом; приложение читает данные при двух ключах и **не читает без предыдущего**, пока ключи не перезавёрнуты; ключ, созданный во время ротации, завёрнут новым; перезавёртывание меняет только обёртку, ключ данных и сохранённый шифртекст остаются теми же; повтор ничего не меняет; один нечитаемый ключ останавливает всё без изменений; ключи владельцев (V2) не трогаются; невалидный предыдущий ключ — ошибка, не молчаливый пропуск; команда проходит всю ротацию и не печатает ключей.
* PostgreSQL 16, скрипты на заглушках, мутации — результаты в `docs/development-progress.md`.

## 8. Что проверено (EN-3b)

* `backend/tests/test_en3b_data_key_rotation.py` (18): статус показывает, каким ключом сколько значений; `start` делает новый активный ключ, старый неактивный, кэш ключа в процессе сбрасывается, новый ключ завёрнут ключом сервера; `reseal` переносит все значения на новый ключ, **читаются те же тексты**, `updated_at` не двигается, повторяем и останавливаем (`--limit`), трогает только значения своего владельца, нерасшифровываемое считает и не трогает, открытые значения не трогает; `retire` отказывает, пока старый ключ что-то шифрует, затем удаляет, и данные читаются одним новым ключом; вторая смена до конца первой отказывает; значение, записанное старым ключом после `start`, находится следующим `reseal`; команда проходит всю смену и не печатает ключей.
