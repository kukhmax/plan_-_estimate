# Шифрование данных клиентов, шаг EN-2b-2 — документы и протоколы

Статус: **EN-2b-2 готов локально (2026-10-18), не выложен.** Бэклог-пункт, **не этап дорожной карты**. Предыдущие шаги: EN-2a и EN-2b-1 (приняты владельцем).

## 1. Что шифруется

Содержимое **договоров** и **пяти протоколов** (передачи помещений, скрытых работ, приёмки, информации и решений, простоя) — всё, где лежат данные заказчика — и **название выданного документа** (в нём название объекта). Всего **37 колонок** в 7 таблицах:

| Таблица | Колонки |
|---|---|
| `contracts` | ответы анкеты, снимок, HTML выданного договора |
| `handover_protocols` | присутствующие, помещения (состояние и замечания), показания счётчиков, заметки, снимок, HTML |
| `concealed_works_protocols` | присутствующие, описание работы, замечания, снимок, HTML |
| `acceptance_protocols` | присутствующие, условия, оценки поверхностей, заметки, снимок, HTML |
| `decision_protocols` | присутствующие, пункты, заметки, снимок, HTML |
| `downtime_episodes` | причина, что нужно от заказчика, дни, присутствующие, влияние на срок, заметки, канал уведомления, снимок и HTML уведомления, снимок и HTML протокола |
| `issued_documents` | название документа |

* **Что остаётся открытым в базе** (технические данные, не данные заказчика): статусы, даты, номера документов и протоколов, размеры и хеш PDF, список помещений документа, названия материалов и партий, суммы к оплате и удержанию в протоколе приёмки. Расчёты («Faktury i zaliczki»: название, номер, контрагент, примечание) — шаг **EN-2b-3**. Свободные заметки помещений, осмотров и **тексты своих напоминаний** в календаре, подписи к фото — в этот шаг не входят (будет решено отдельно по вашему слову).
* **PDF**, отправленные в Telegram, живут в чате, не в базе; сам PDF строится из зашифрованных снимков при выдаче.
* Формат: колонки JSON хранят JSON-**текст**, зашифрованный целиком (`enc1:…`); для приложения ничего не меняется.

## 2. Миграция 0063 (без потери данных)

* JSONB / VARCHAR(255) → **TEXT** (`USING ::text`): старые значения не меняются и читаются как раньше; шифртекст длиннее прежних пределов.
* Откат миграции **откажет**, пока в этих колонках есть шифртекст (прежний код его не прочитает).

## 3. Порядок выкладки (скрипт сам делает всё по порядку)

**Строгое чтение** (включено после EN-2b-1) на время миграции и перекодировки **временно выключается**: иначе старые документы отклонялись бы, пока не перекодированы. Скрипт выключает его, делает работу и **включает снова** на воротах S. Если он остановится посреди — строгое чтение остаётся выключенным (безопасно).

1. **Бэкап A9 под голову 0062 не старше суток** — он нужен до миграции. Образы бэкапа собираются из ветки, чья последняя миграция совпадает с базой; после EN-2b-2 ветка `backlog-client-encryption` заканчивается миграцией 0063, поэтому **новый** бэкап под 0062 из неё сделать нельзя. Подходит последний бэкап под 0062 (после EN-2b-1: `20261018T145622Z-f8a60ead`); скрипт сам проверяет его возраст (≤ 24 ч) и покажет его номер. Если он старше суток — скажите мне, добавлю закрепление коммита для бэкапа.
2. Скрипт (в **новой** сессии):
   `cd ~/apps/plan_-_estimate && git fetch -q origin backlog-client-encryption && git show origin/backlog-client-encryption:docs/CLIENT_ENCRYPTION_EN2B2_DEPLOY_RU.sh > ~/deploy_en2b2.sh && bash ~/deploy_en2b2.sh`
3. Ворота **M**: `МИГРАЦИЯ 0063 ДА` — миграция + пересоздание backend (30–60 секунд) со строгим чтением выключенным; скрипт проверяет: 37 колонок стали TEXT, число строк то же.
4. Ворота **R**: `ПЕРЕКОДИРОВКА ДА` — старые значения (включая документы) → шифртекст, затем `verify`: открытых 0, нерасшифровываемых 0.
5. Ворота **S**: `СТРОГОЕ ЧТЕНИЕ ДА` — строгое чтение включается обратно; скрипт читает **все строки 11 зашифрованных таблиц** в строгом режиме и сверяет число строк с базой.
6. После `ВСЁ PASS`: чек-лист (раздел 4), затем бэкап под новую голову: `BACKUP_BRANCH=backlog-client-encryption BACKUP_HEAD=0063_encrypted_documents bash ~/backup_a9.sh`.

Скрипт можно запускать повторно: он узнаёт, что миграция уже применена, не двигает тег `pre-en2b2` и не требует лишних ворот.

## 4. Чек-лист после выкладки (на телефоне, PL и RU)

* Откройте **уже выданный** договор и каждый выданный протокол: данные, присутствующие, замечания на месте.
* Сформируйте **новый** документ (например, договор или протокол): PDF приходит в чат, в нём имена и адреса как должны быть; запись появилась в журнале отправленных документов с названием.
* Измените черновик протокола (присутствующие, заметка), сохраните, откройте снова.
* Журнал отправленных документов, карточка объекта → документы: названия читаются.
* Клиенты, объекты, календарь, архив — как раньше.

## 5. Откат — порядок и предел

* **До ворот R** (ничего не перекодировано): миграция вниз командой из сообщения скрипта (`alembic downgrade 0062_data_keys`), затем образ `pre-en2b2`; верните `DATA_STRICT_READ=true`, если он был.
* **После перекодировки** образ до EN-2b-2 документы не прочитает, откат миграции откажет: только **вперёд** новым выпуском или из бэкапа A9.
* Строгое чтение выключается без потерь (`DATA_STRICT_READ=false`, пересоздать backend).
* `DATA_KEK` по-прежнему нельзя терять и менять.
